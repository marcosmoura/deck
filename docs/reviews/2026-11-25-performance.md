# Performance review, 25 Nov 2026

Sub-spec [04](../specs/2026-11-23-reviews/04-performance.md) of DECK-26 took the first round of measurements; [05](../specs/2026-11-23-reviews/05-performance-second-round.md) took the second and finishes this report (sections marked "round two"); [06](../specs/2026-11-23-reviews/06-performance-fixes.md) makes the fixes. The code analysis (wake-up sources, the keystroke and output paths, suspected findings) was done by read-only reviewers before any measurement; its notes are not kept in the repository, and this report states what the measurements below show about each suspected finding. Ids (`F-n` for the daemon, `G-n` for the attach client) are the analysis's and stay stable.

- `crates/deck/tests/support/mod.rs`: `Harness::watch` and `Harness::watch_cell`. ## Measurements

### Keystroke latency (`latency`)

200×60 window, sidebar on, `cat` in the focused terminal so the line discipline echoes each key at the cursor. One key every 300 ms, Enter every 40 keys; the cell watch is armed on the cursor's cell before the key is written. Load average (1 minute) 17.9 at the start, 10.4 after the rest samples, 8.0 after the flood samples and 7.0 at the end: the machine was recovering from a spike (97.8 over five minutes), so the figures are from a busy but falling load.

| Case                                                              | n   | min     | p50     | p90     | p99     | max     |
| ----------------------------------------------------------------- | --- | ------- | ------- | ------- | ------- | ------- |
| Echo at rest                                                      | 200 | 17.5 ms | 19.8 ms | 21.1 ms | 23.8 ms | 28.8 ms |
| First output after the key, at rest                               | 200 | 0.4 ms  | 1.1 ms  | 1.9 ms  | 6.0 ms  | 7.8 ms  |
| Echo with a flood in another terminal of the panel                | 199 | 1.9 ms  | 8.6 ms  | 18.8 ms | 20.0 ms | 20.3 ms |
| First output after the key, during the flood                      | 199 | 0.1 ms  | 7.0 ms  | 14.5 ms | 17.6 ms | 19.1 ms |
| Ctrl-C into a flood in the same terminal, time to the next prompt | 10  | 19.7 ms | 36.3 ms | 38.1 ms |         | 39.1 ms |

The flood is a loop of `cat` over a file of varying 100-column lines (the first version, a constant line, let the screen stay unchanged and the first output could not be told from the echo; it was replaced and `latency` rerun, so these figures are the rerun's). At rest the first output after a key comes after 1.1 ms (median) and is not the echo: it is the client's no-op draw (G-1). The echo shows 18 ms later. During the flood the first output is the flood's own frames, and the echo (median 8.6 ms, p90 18.8) is no worse than at rest: a flood frame that redraws the cell can show the echo early, so the median is a lower bound of the echo time, not a separate gain. One key of 200 was not echoed within 5 s of the cell being armed and is counted as lost. The flood terminal had read 5.3 GB by the end. Ctrl-C into the flood gives the prompt in 36 ms (median, max 39 ms); the 306 ms outlier and 130 ms p90 of the first run, which ran at a load of 142, did not come back at a load of 7 to 18, so they were the machine's.

### One slow terminal stalling the others (`stall`)

Terminal A loops `cat` of a 64 KiB file of `a ESC [ 65535 b` (the repeat-character sequence); 30 keys and 30 `deck ls` were timed in another terminal (B, `cat`) for each case, 250 ms apart. Load average (1 minute) 19.3 at the end of the scenario (`load_average` in `stall.json`).

| A is                        | Key echo p50 / p99 / max | `deck ls` p50 / p99 / max | Daemon CPU     |
| --------------------------- | ------------------------ | ------------------------- | -------------- |
| absent                      | 19.4 / 22.4 / 22.4 ms    | 18.9 / 24.5 / 24.5 ms     | 0.6% of a core |
| in the same, active panel   | 17.6 / 18.8 / 18.8 ms    | 4.5 / 7.6 / 7.6 ms        | 1.01 cores     |
| in a background panel       | 18.2 / 19.0 / 19.0 ms    | 4.5 / 7.9 / 7.9 ms        | 1.00 cores     |
| in a session with no client | 18.1 / 19.0 / 19.0 ms    | 4.4 / 6.9 / 6.9 ms        | 1.00 cores     |

The slow sequence keeps A's emulator thread at one full core (about 2.1 million bytes read in 10 s, in reads of about 1 KiB at about 45 µs per sequence), yet no key echo is slower: F-3 is not shown with this input. What the data bounds: with the state lock held across a feed, B's request waits at most for one read's feed, about 5 ms on macOS for these repeats; the premise of 0.3 s per 64 KiB chunk does not occur because feeds are per read. The key metric cannot see a stall of that size: the echo sits behind the client's 16 ms throttle (G-1), and delays under about 13 ms vanish into it. The `deck ls` column can: with A streamed in the active panel 10 of 30 `ls` samples were above 5.5 ms, in a background panel 6 of 30, with no client 1 of 30 (p99 7.6 ms against 6.9). That is a hint of a few ms of waiting, not a proof; it is small and the load was 19. The `absent` row's `deck ls` (p50 18.9 ms) is spoiled by machine load and is not a baseline. The PNG variant, which decides F-3, is in round two below.

### One slow terminal with PNG commands (`stall`, PNG variant)

Terminal A loops `cat` of a file of 200 `a=t,f=100` kitty commands, each a 111-byte PNG that declares 4096×4096 pixels (the decoder allocates the declared size). 60 keys and 60 `deck ls` timed in another session, 250 ms apart, in the same three placements of A as before. Load 22.5 at the start, 7.9 at the end. The slow-text rows come from the same run.

| A is                 | Key echo p50 / max | `deck ls` p50 / p90 / p99 / max          | Daemon CPU |
| -------------------- | ------------------ | ---------------------------------------- | ---------- |
| absent               | 19.1 / 28.3 ms     | 11.2 / 13.3 / 15.1 / 15.6 ms (see below) |            |
| repeat, active panel | 11.7 / 17.8        | 4.1 / 4.7 / 4.9 / 6.4                    | 1.0 core   |
| repeat, background   | 18.4 / 19.0        | 4.4 / 4.8 / 7.4 / 10.5                   |            |
| repeat, no client    | 18.0 / 19.0        | 4.1 / 4.6 / 6.2 / 6.9                    |            |
| PNG, active panel    | 17.7 / 18.7        | 6.0 / 8.7 / 9.3 / 9.8                    | 1.0 core   |
| PNG, background      | 18.0 / 19.1        | 4.9 / 8.7 / 9.4 / 9.5                    |            |
| PNG, no client       | 18.1 / 19.0        | 4.6 / 7.2 / 8.6 / 9.1                    |            |

Verdict on F-3: not refuted; it stays planned for sub-spec 06. With A printing the PNG commands, `deck ls` in the other session waited 0.5 to 1.9 ms longer at the median than with the repeat sequence and 2 to 4 ms longer at p99 (worst 9.8 ms; the repeat's worst was 10.5 ms in the background case), and its p90 was 7.2 to 8.7 ms against 4.6 to 4.8. That tail is consistent with the state lock held across a feed, but it could as well be allocator or virtual-memory pressure from the 64 MiB allocations, which this run does not separate. These feeds are also short: a PTY read is about 1 KiB, holds about 9 commands at 0.59 ms each, so a feed lasts about 5 ms; the "tens of milliseconds" the sub-spec asked for was not reached, because a tiny PNG is cheap to decode even when it declares a lot. Other terminals' key echo did not change (the 16 ms throttle hides anything under about 13 ms). The `absent` row's `deck ls` is the same oddity as in round one (58 of 60 samples between 9.2 and 15.6 ms with no terminal A, load 8 to 22): it is systematic and unexplained, not shown to be a load spike, so no row of this table is a clean baseline for `deck ls`. For sub-spec 06: a fix of F-3 needs an input that makes one feed long (a valid, highly compressible 4096×4096 PNG whose decode runs in the feed of its last chunk) or a test seam that blocks one emulator, to show a before and an after. Not measured: Linux, where PTY reads may be larger and the wait longer.

### Paste (`paste`)

Text into `cat > <file>` in the client's terminal, 100-column lines, three runs per size; completion is the target file reaching its size (not the echo, which the tty may drop when its output queue is full), bounded at 120 s. A real paste is the text between the bracketed-paste markers (`ESC [ 200 ~`, `ESC [ 201 ~`), which the client forwards as one `Input` (the client turns bracketed paste on). Load 9 at the start, 8.5 at the end, niced.

| Case                                        | Complete p50 (min to max) | First echo p50 (when the first line was seen) |
| ------------------------------------------- | ------------------------- | --------------------------------------------- |
| Paste 64 KiB                                | 17 ms (17 to 25)          | not seen (the screen had scrolled past it)    |
| Paste 256 KiB                               | 91 ms (64 to 116)         | 42 ms                                         |
| Paste 1 MiB                                 | 274 ms (268 to 353)       | 119 ms                                        |
| A burst of 64 KiB typed keys (no markers)   | 980 ms (969 to 1,002)     | 36 ms                                         |
| Bare PTY, 64 KiB / 256 KiB (no deck)        | 35 ms / 62 ms             |                                               |
| `deck send -` 64 KiB (returned / complete)  | 23 ms / 35 ms             |                                               |
| `deck send -` 256 KiB (returned / complete) | 18 ms / 58 ms             |                                               |

A real paste through deck is as fast as the bare PTY at these sizes (1 MiB in 0.27 s is about 3.7 MiB/s; the bare PTY did 4.0 MiB/s with 256 KiB), and `deck send -` is as fast: exit status 0 and empty stderr, the file complete after 35 and 58 ms. So pasting is not slow. What is slow is the burst of typed keys, the form that reaches the client when the outer terminal sends text without the markers (about 65 KiB/s, 15 µs per byte): the client sends one `Input` per key and each waits for the emulator (F-4). The earlier version of this scenario sent its text in that form and measured 0.77 s for 64 KiB and 3.3 s for 256 KiB; those were the typed burst, not a paste, and the rewritten scenario's burst (0.98 s for 64 KiB) agrees. G-8's branch (`reader.rs:96-99`, a 50 ms wait when the terminal polled ready but nothing was read) is reached by a typed burst too, not only in the middle of a bracketed paste: on Linux it hung the client (G-13), which the re-arm (`rearm_stdin`) now prevents; the paste above, which reaches 1 MiB in 0.27 s, shows no 50 ms stalls. The first version's `deck send` run of 256 KiB, which never completed in 300 s, waited for the last line to show on the terminal; the hypothesis (not tested) is that the tty dropped echo when its output queue was full, so the line never appeared, which the size check no longer depends on. No profile of the typed-burst path was taken.

### Profiles (samply)

- **Daemon during `throughput`** (a daemon with no client, `cat` of the 256 MiB file, 2,000 Hz, wall-clock samples): the emulator thread (`emu-N`) spends 82.9% of its samples blocked in `semaphore_wait_trap` and 5.2% in `semaphore_signal_trap`; its real work is `vtPrintAscii` 2.2%, `PageList.pointFromPin` 1.0%, `Screen.cursorScrollAbove` 0.9%, `vt_write` 0.7%. The `pty-reader` thread spends 75.4% blocked in `semaphore_wait_trap` (waiting for the emulator in `EmuThread::call`) and 6.3% signalling; its own work is `read` 5.5%, the kitty file scanner 2.2%, `Osc7Scanner::feed` 1.6%, `incomplete_tail` 1.2%, `poll` 3.0%. The two threads wait for each other most of the time: the pipeline is bound by the per-chunk thread round trip, not by copies or by the emulator's work (F-8). The tokio workers are idle (80% in `kevent`).
- **Client during the frame benchmark** (decode and draws, 4,000 Hz): 26.0% of the samples are in `unicode_segmentation::Graphemes::next` (per-cell segmentation in `set_stringn`), 8.9% `Buffer::index_of`, 8.0% `Cell::eq` (the diff), 7.5% `malloc`, 7.3% `draw_screen`, 5.8% the buffer diff iterator, 3.5% `Vec::extend_with` (buffer reset), 3.1% `set_stringn`; postcard deserialisation (`Run`, `String`, `SeqAccess`) about 6%. A draw is dominated by painting the panel into a scratch buffer and diffing it, not by the write calls (G-4).
- The `idle_spinner` profile was not taken separately: the benchmark's draw profile is the spinner's tick, which draws the whole screen each time (a no-op draw is 0.5 ms, so 60 draws a second is 3% of a core, the figure measured).

## Where the keystroke time goes

At rest the echo takes 19.8 ms (min 17.5, max 28.8), of which the first 1.1 ms is the client's no-op draw. The echo frame arrives later and is drawn when the client's 16 ms throttle, restarted by that no-op draw, lets it. So, by inference from the code and the 1.1 ms, about 16 ms of the 19.8 are the throttle and the remaining 3 to 4 ms the whole path through the daemon, the PTY and back. Fixing G-1 should bring the median near 5 ms; whether it reaches the target depends on the daemon's frame pump (16 ms after output, in the daemon) which the data cannot separate: min 17.5 ms means a key never gets through faster than that today.

## Spec claims that differed from the code or from the measurements

- The analysis expected an idle daemon at 0.25 to 0.35% of a core; it is 1.59%. The wake-up count (475 a second against 485 estimated) was right; the cost of a wake-up is about 33 µs, not 6.
- The estimate of 1 to 1.5 MiB per idle terminal was 0.36 MiB.
- A full 200×60 styled frame is 0.82 ms to build, under the 1 to 3 ms estimate; a client draw is 0.5 ms (estimate 0.3 to 1) and a whole-screen draw 0.8 ms (estimate 1 to 3); decoding at 8 runs per line is 18 µs (estimate 50 to 150).
- A key typed at rest takes 19.8 ms in a release build; the analysis measured 22 to 23 ms in a debug build and expected 17 to 18 in release.
- `deck stats` reports the terminal's size as `cols` and `rows`, not `size`.
- Round two: a tiny PNG that declares a large image costs 0.6 ms, not 10 to 25; a live upgrade of 30 big terminals takes 0.4 s, not 1 to 5; the client uses 4 to 6 MiB in text, not tens; the environment in the hello costs under 1 ms; the client's footprint did not fall after the terminals with images closed (the code drops their pixels; the cause is open).
- A panel holds a limited number of terminals (a new terminal is refused with "not enough room for another terminal"), so scenarios that need many terminals use panels.
