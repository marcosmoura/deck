# Architecture

Read when you write a spec or touch code. This page holds the decisions every spec builds on. A spec that changes one of them updates this page in the same change.

## Process model

```text
 terminal emulator (Ghostty, iTerm, …)
 └─ deck (client)  ── Unix socket ──  deck daemon ──┬─ PTY ─ $SHELL / agent
    ratatui UI, input                 sessions,     ├─ PTY ─ …
                                      emulation,    └─ state.json
 deck ls / new-terminal / … ────────┘ persistence
 (control)
```

- **One daemon per user**, started on demand by the first `deck` command that needs it (`deck daemon` re-execs the same binary in a new session with `setsid`, stdio to the log file). It owns every PTY, runs one terminal emulator per PTY, and keeps doing so while no client is attached. A PTY is opened and its process started (`fork`, `exec`) on tokio's blocking pool, never on an async task or under the state lock; each terminal then has blocking reader, writer and wait threads. Each terminal's emulator lives on a thread of its own (`emu-<terminal id>`), which creates and owns it and runs, one at a time and in order, the closures the daemon sends through `TermHandle::with_emu` (the caller blocks until the result is back; a panicking closure is logged and returns `None`; after `release` the thread ends and `with_emu` returns `None` at once). A PTY resize runs on that thread too, so the PTY and the emulator change size as one step. Input waiting for a program that does not read it is capped at 1 MiB per terminal (one larger paste into an empty queue still goes through); past that, input is dropped with one warning in the log. It exits when the last session is killed, or on `deck kill-server`.
- **Emulator** (`deck-daemon/src/emu.rs`, DECK-19): `ghostty_vt::Terminal` (Ghostty's `libghostty-vt`) with a render state, read into `Frame`s: a full frame reads every row; a damage frame reads the rows the render state reports dirty, or all of them when the whole screen is dirty or the display is scrolled back, then marks them clean. Scrollback is a byte budget for `libghostty-vt`, set at creation and pruned in whole pages: `Emu` asks for 2,560 bytes per configured line (a 250-column line takes about 2,000) plus 1 MiB, which is 26,648,576 bytes for the default 10,000 lines, and holds at least that many lines up to 250 columns (11,673 measured at 250, about three times as many at 80, 2,700 at 1,000: wider terminals keep fewer lines). `history`, scrolling back and `capture` stop at the configured number of lines, so the extra lines of a narrower terminal are hidden, not freed. The emulator answers what a terminal answers on its own (DA1 `CSI ? 6 c`, DA2 `CSI > 0;2600;1 c`, size reports with the client's cell size, 8x16 pixels while none is known, OSC 4/10/11 from the xterm palette and the colours of the client the session follows, which `output` hands to `Emu::set_colors` before each write, so a program that sets OSC 10/11 itself gets its own colour back). It always answers `CSI ? u` (kitty keyboard flags), `CSI 16 t` (cell size) and XTVERSION, which the daemon never did and cannot switch off, so `Emu` drops those replies; the `CSI 16 t` one passes once a client has reported its cell size, and the XTVERSION one passes once a name is set (`Emu::set_xtversion`, handed the outer terminal's name by `output` like the colours: the name of the client the session follows when it attached with `images` and an `outer_name`, kept in `session_names` by `publish_colors`; else none, and the query stays unanswered). Programs such as Claude Code show kitty images only when the terminal names itself `ghostty` or `kitty`. Its default cursor style is the hollow block, which no `DECSCUSR` selects, and the frame reports it as `CursorShape::Default`. **Cell size**: the daemon keeps the cell size in pixels of the client the terminals follow (`Attach.cell`, `Viewport.cell`, `ReloadViewport.cell`; `None` when the outer terminal reports no pixel size) with its viewport, and when either changes (a font zoom changes only the cell size) it passes it to every emulator of the session (`Emu::resize_with_cell`, so `CSI 14/16 t` and the image grid sizes use it) and sets the PTY's pixel size to `cols x width` by `rows x height` (`ws_xpixel`, `ws_ypixel`; 0 by 0 while unknown), also in `sync_pty`; a terminal created later starts with it. **Kitty graphics** are on in every emulator (`emu/graphics.rs`): 64 MiB of image storage per screen, the emulator's file, temporary-file and shared-memory mediums are off (a path the program names, such as a FIFO or `/dev/shm/<name>`, can block the emulator thread). Instead the PTY reader thread of each terminal runs the output through a scanner (`emu/files.rs`, state per terminal, working across output chunks, touching only `ESC _ G` APCs of at most 8 KiB of printable bytes; any other byte but ESC ends the command, as in Ghostty) before `output` hands it to the emulator, so file I/O never runs on the emulator thread or under the state lock. It rewrites `t=f` and `t=t` commands into direct transmission: it base64-decodes the path (absolute), resolves it with `canonicalize` (so `..` and symlinks count), refuses what is under `/proc`, `/sys` or `/dev` other than `/dev/shm`, opens the resolved path with `O_NONBLOCK`, `O_NOCTTY` and `O_CLOEXEC`, requires a regular file, reads at most 64 MiB (honouring `S` and `O`) and streams it as `t=d` commands of 3072 file bytes (4096 base64 bytes; `m=1`/`m=0`, later chunks keep only `m` and `q`). The emulator receives the output in pieces of at most 64 KiB, one `with_emu` each, so a burst of file commands holds neither a large buffer nor the emulator. Each terminal may read 128 MiB of files per second; past that, commands pass unchanged. A `t=t` file is deleted once it is opened when it is in a temp directory and named with `tty-graphics-protocol`, even if the read is then refused. A command that fails any check passes on unchanged and the emulator answers it with an error; `t=s` is always refused, and a PNG decoder (the crate's `RustPngDecoder`, wrapped to expand the greyscale PNGs it leaves at 1 or 2 bytes per pixel, which Ghostty rejects; palette and 16-bit PNGs come out as RGBA8 from the crate). The decoder is stored per thread by `ghostty-vt`, so `Emu::new` installs it on the emulator's thread, under one process-wide lock because each install also sets a process-global C option (the only process-global state besides the crate's optional logger, which deck does not set). A program's `a=q` query is answered by the emulator. `Emu::placements()` lists the placements of the active screen that touch the viewport as shown (`Placement`: screen, image id and generation, `Placed { col, row }` relative to the viewport, negative when it starts above or left, or `Virtual` once per image; `cols x rows` from `grid_size`, saturated to `u16`; source rectangle and rendered pixels), lower `z` first; `Emu::image(screen, id)` copies an image's pixels as RGB or RGBA; `Emu::images_changed()` tells whether the storage generation or the placement list changed since the last call. Handles from the crate are valid only until the next mutating call, so all three copy first. `damage_frame` counts a graphics change as damage (it is built whether or not a row changed) and every frame carries `Emu::placements()` in `Frame.images`; `Emu::image_generations(ids)` reads, without pixels, which of some images the active screen's storage still holds. The daemon sends them to clients that attach with `images` (see Image transport under Protocol). Synchronized output (mode 2026) is only recorded by `libghostty-vt`: while it is set `damage_frame` returns `None` and the damage waits; 150 ms after the daemon's injected clock first saw it, or when the program resets it, the next frame carries everything (`Emu::hold_remaining` tells the frame task when to look again).
- **Clients** are short or long lived `deck` processes. The **attach client** (`deck`, `deck attach`) draws the UI for one session. **Control clients** (`deck ls`, `new-space`, `new-panel`, `new-terminal`, `focus`, `close`, `rename-panel`, `send`, `send-keys`, `capture`, `wait`; DECK-05) send one request, print the answer and exit. They never start a daemon or create a session. Both kinds speak the same protocol on the same socket; `DECK_SOCKET`, when set, wins over the [paths](#paths).
- **Single instance.** The daemon holds an exclusive lock on `deck.lock` (`std::fs::File::try_lock`) for its lifetime and writes its pid into it, then removes a leftover `deck.sock` and binds it; only the daemon ever removes the socket. It also holds `state.lock` next to `state.json`, so two daemons started with different runtime dirs (another `TMPDIR` or `XDG_RUNTIME_DIR`) can never share one state. A client that gets no answer on the socket (no daemon, or one that is shutting down and says `Bye` or drops the connection) starts the daemon and waits up to 3 s for one that answers. `deck kill-server` asks the daemon to stop; when the daemon speaks another protocol version or does not answer, it sends `SIGTERM` to the pid in `deck.lock` (the same clean save path). Either way it returns only once the lock is released (up to 5 s), so a `deck` right after it never races the old daemon.
- **Peer check.** The daemon accepts only connections whose peer uid equals its own (tokio's `UnixStream::peer_cred()`, no `unsafe`). Client and daemon `lstat` the runtime directory and refuse it unless it is a directory owned by the effective uid with mode `0700`, so a squatted `/tmp/deck-<uid>/` never receives a client's environment.

## Crates

| Crate         | Path                  | Owns                                                                                                                                                   |
| ------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `deck-core`   | `crates/deck-core/`   | Model types, layout engine, protocol messages and framing, key encoding, config parsing, paths. Pure: no I/O beyond `std::path`, no threads, no async. |
| `deck-daemon` | `crates/deck-daemon/` | The daemon: socket server, sessions, PTYs, emulation (`ghostty-vt`), frames, persistence, agent status. Library crate.                                 |
| `deck-tui`    | `crates/deck-tui/`    | The attach client: screen mirror, rendering (ratatui), input handling, key bindings. Library crate.                                                    |
| `deck`        | `crates/deck/`        | The binary: CLI (clap), daemon start-up, control commands, wiring. Holds the end-to-end tests in `crates/deck/tests/`.                                 |

`deck-daemon` and `deck-tui` never depend on each other. Both depend on `deck-core`.

## Model

```text
Daemon
└─ Session        id, name, projects (ordered), active project
   └─ Project     id, name, root dir, panels (ordered), active panel, collapsed
      └─ Panel    id, name + name source (default | manual | auto), terminals (ordered), layout ratios, focused terminal
         └─ Terminal  id, launch spec (shell or command + args, cwd, env), title (OSC 0/2), cwd (live), exit status, agent
```

- IDs are `u64` newtypes (`SessionId`, `ProjectId`, `PanelId`, `TerminalId`) from one daemon-wide counter that is persisted, so an ID is never reused.
- **Names.** Session names are unique within the daemon; project names within a session; panel names are free. A panel's `name_source` is `default` (generated), `manual` (set by the user; never overwritten automatically) or `auto` (set from what runs in the panel, DECK-09). A panel whose `name_source` is not `manual` is named after its _source terminal_ (its first terminal in grid order that has an agent, else its focused one) by the pure `deck-core::naming::auto_name`: an agent's title without its leading spinner and status glyphs (unless it is only the program or a product name), else the first line of its `first_prompt`; any other program's title, else its `program`; at most 32 display cells, control characters removed. `Terminal.program` follows the foreground process on the 1 s detection tick (`agents::program_name(argv)`: login dash and extension removed, an interpreter unwrapped for a script, deck's resume wrapper looked through) and keeps its last value when the process cannot be read. The daemon recomputes the name of the panel concerned after a title change, a changed program or agent state, an agent event, a change of its terminals or of the focused one, and `Action::AutoNamePanel`, and sends a view only when the name (or the title, apart from an agent title's spinner) changed. A manual rename locks the name; `AutoNamePanel` unlocks it.
- **Projects** are a name plus a root directory. New terminals in a project start in its root. Everything the user sees or types calls them **spaces** (sidebar, prompts, help, config keys such as `new_space`, `deck new-space`, `--space`, the `spaces` key of `deck ls --json`); the code, the protocol and `state.json` keep the name project.
- **Lifecycle.** When a terminal's process exits, the terminal is removed, unless it was created with `keep` (control API), in which case it stays with its exit status shown. A panel with no terminals is removed. A project with no panels stays in the sidebar, empty. A session stays until it is killed. The daemon exits when no session is left.
- **Environment.** A session remembers the environment of the client that created it (sent in `Hello`); its terminals get that environment minus `DECK_*`, `TMUX`, `TMUX_PANE`, `COLUMNS`, `LINES` and the client's `TERM_PROGRAM*`, plus `TERM=xterm-256color`, `COLORTERM=truecolor`, `TERM_PROGRAM=deck`, `TERM_PROGRAM_VERSION=<deck's version>` and the `DECK_*` variables. On every attach, an allowlist is refreshed from the attaching client's `Hello` for terminals started afterwards: `SSH_AUTH_SOCK`, `SSH_CONNECTION`, `SSH_TTY`, `DISPLAY`, `WAYLAND_DISPLAY`, `XAUTHORITY`. The daemon's own environment is otherwise never passed on. The one exception: sessions restored after a daemon restart (DECK-04) use the daemon's start environment, which is the `Hello` environment of the client that started it. `state.json` never stores a session's environment, only `--env` additions given through the control API.
- **Focus** (active project, active panel, focused terminal) is stored per session in the daemon, so every client attached to a session sees the same focus.

## Layout

The terminals of a panel are placed by one pure function in `deck-core::layout`:

```rust
pub fn layout(area: Rect, n: usize, ratios: &Ratios) -> Vec<Rect>
```

**Shape.** `n = 1`: the whole area. Terminals keep the order they were created in (no swapping). `n` even: a grid of `cols × rows = n` with `cols ≥ rows` and `cols − rows` as small as possible (2 → 2×1, 4 → 2×2, 6 → 3×2, 8 → 4×2, 12 → 4×3). `n` odd and > 1: terminal 1 takes the left part at full height (the **main** split); the other `n − 1` fill the right part as a grid with `rows ≥ cols` (the even rule turned on its side). Terminals fill a grid left to right, then top to bottom.

```text
n=2              n=3              n=4              n=5
┌──────┬──────┐  ┌──────┬──────┐  ┌──────┬──────┐  ┌──────┬───┬───┐
│      │      │  │      │  2   │  │  1   │  2   │  │      │ 2 │ 3 │
│  1   │  2   │  │  1   ├──────┤  ├──────┼──────┤  │  1   ├───┼───┤
│      │      │  │      │  3   │  │  3   │  4   │  │      │ 4 │ 5 │
└──────┴──────┘  └──────┴──────┘  └──────┴──────┘  └──────┴───┴───┘
```

**Ratios.** `Ratios { main: Option<u16>, cols: Vec<u16>, rows: Vec<u16> }` in per-mille. `main` is the left part's share for odd `n` (default 500); `cols` and `rows` are the grid's column widths and row heights (default equal). All arithmetic is integer, in `u32`: the main split's left width is `(width × main + 500) / 1000`, and grid boundaries are cumulative, `floor(len × (sum of shares up to the boundary) / 1000)`, so the last track takes the remainder and a dragged boundary lands exactly on the pointer cell. With one terminal the rect is the whole panel area and the terminal has no border; with two or more, each rect includes the terminal's 1-cell border and the PTY gets the inner size (`width − 2`, `height − 2`, at least 1×1). When `n` changes, the ratios are adapted, not reset (`Ratios::adapt`), relative to the defaults: the layout is read as full-width columns (for odd `n`, the main split is the first column and the right grid's columns follow, scaled to the rest) and rows (the grid's rows; for odd `n`, the right grid's rows); each surviving track becomes `old_share × default_new / default_old`, an added track gets its default share, and the list is renormalised to 1000 with the floor-and-remainder rule. So `adapt(default_for(a), a, b) == default_for(b)` for every `a`, `b`: untouched layouts always follow the shape rule, and custom ones keep their proportions. Stored ratios are never overwritten because they do not fit: when they would put a terminal below the 10×3 minimum at the current viewport, `layout::fit` gives a clamped copy for that viewport only, which the daemon and the client both use,, and the stored ratios return when the window grows. Only `reset_layout` restores the defaults. `layout::panel_rects` is the one call that gives both sides the drawn grid (`layout` of the `fit` ratios at the 10×3 minimum, `layout::MIN_INNER`), and `layout::has_room_for` is the check behind `NewTerminal`'s refusal; the actions `NewTerminal`, `CloseTerminal`, `FocusTerminal` and `FocusDirection` change a panel's terminals and focus. Resizing moves one boundary in the direction of the key, in steps of 50 per-mille (at least one cell): the focused terminal's edge on that side when it has one, else its opposite edge. It never takes a terminal below a 10-column or 3-row inner size. A client sends new ratios as `SetRatios { panel, n, ratios }`, refused when `n` is no longer the panel's terminal count. Details: DECK-03.

The daemon and the client both call `layout` with the same inputs: the daemon to size PTYs, the client to draw. macOS can lose a PTY resize although the ioctl succeeds, so the daemon compares the real PTY size (`TIOCGWINSZ`) with the wanted one on every layout pass and re-checks it 50 ms, 250 ms and 1 s after each resize, resizing again when it differs. A program that changes its own window size (`stty cols 100`) is put back to the layout size at the next layout pass or within 1 s, as other multiplexers do. The client reports the size of its panel area (`Viewport`, or `ReloadViewport` when a config reload moved the sidebar: it is recorded without making that client the one the terminals follow); at attach it reports the outer window and the daemon computes the area with `layout::panel_area(outer, config.sidebar_width, sidebar_visible)`, which the client calls with its own width to draw too. After the first `SessionView` of an attach or a session switch the client sends `Viewport` when its own area differs from the one the daemon derived (a dragged width, a sidebar hidden with `toggle_sidebar`).

## Protocol

- **Framing**: a `u32` little-endian length, then a `postcard` payload of `ClientMsg` or `ServerMsg` (in `deck-core::protocol`). Maximum frame 16 MiB.
- **Handshake**: the client's first message is `Hello { version, role, cwd, env, colors }` (`colors`: the outer terminal's foreground and background, queried with OSC 10/11 at attach with a 200 ms timeout, `None` when it does not answer; answers that arrive after the timeout are taken out of the input for 3 seconds, so they never reach a terminal as keys. The same start-up query also asks for the terminal's name (XTVERSION, `ESC [ > 0 q`) and for kitty graphics support (a one-pixel `a=q` query, `i=31`) before DA1; both replies are parsed like the colours and swallowed when late (`deck-tui/src/colors.rs`); the daemon answers programs' OSC 10/11 queries with them, else a fixed fallback) with `role` = `Attach { session, create, cols, rows, cell, images, outer_name }` (`cols × rows` is the client's outer window size, `cell` its cell size in pixels from crossterm's `window_size()` (`None` when it reports none), `images` whether it can show images, `outer_name` the outer terminal's XTVERSION reply (above; kept when it is printable ASCII text of at most 64 characters, e.g. `ghostty 1.2.0`; `None` when it gave none), which the daemon gives to the programs' XTVERSION queries when `images` is set; the daemon derives the panel area from its config with `deck-core::layout::panel_area`, so a new session's first terminal starts at the right size) or `Control`. A version that differs from `PROTOCOL_VERSION`, or a first frame that does not decode past `version`, gets `Bye { reason: VersionMismatch { daemon } }`, and the client tells the user to run `deck kill-server` (which also stops a daemon of another version, see [Process model](#process-model)). `Hello` stays the first `ClientMsg` variant with `version` first, and `Bye`/`VersionMismatch` keep their layout, so mismatched versions can always say so.
- **Attach traffic**: the client sends `Viewport { cols, rows, cell }` (its panel area and cell size; also sent when only the cell size changed, which the client sees on `SIGWINCH`), `Input { terminal, bytes }`, `Action(..)` (focus, new terminal, rename, …), `Scroll { terminal, .. }` and `Detach`; each `Action` is answered by `ActionResult(Result<(), ActionError>)`, in order. Control and attach clients also send `Request`s (`ListSessions`, `KillServer`, `NewSession`, `KillSession`, `RenameSession`), answered by `Response`. The daemon sends `SessionView` (the attached session's tree with names, focus and agent status, and `layout_viewport`, the panel area it sized the PTYs for; sent whole whenever it changes) and `Frame` updates for the terminals of the active panel only.
- **Frames**: `Frame { terminal, size, cursor, modes, display_offset, history, lines: Vec<(u16, Line)>, full }`, where `Line` is a list of `Run { col, text, style }` placed at the emulator column of their first cell. A wide character occupies two columns and its spacer cell sends no text; zero-width (combining) characters are appended to their base character; trailing blank default-styled cells are not sent. The daemon sends changed lines (from the emulator's damage tracking), coalesced to at most one frame per terminal every 16 ms, and a `full` frame on attach, on panel change and on resize. `modes` carries what the client needs to encode input (application cursor keys, bracketed paste, mouse reporting mode, focus reporting). `Frame.images: Vec<Placement>` is the terminal's complete list of kitty image placements (DECK-19) in every frame, full or not, for a client that attached with `images`; it is empty for any other client.
- **Image transport** (DECK-19, `deck-daemon/src/images.rs`): pixels travel in their own messages, once per (terminal, screen, image, generation) and client, ahead of the first frame that lists the image. `ServerMsg::Image { terminal, screen, image, generation, width, height, format, offset, total, data }` is one piece of an image's `Rgb` or `Rgba` pixels (`data` at most 4 MiB, `offset` its byte offset, `total` the whole length; the pieces of one image come in order); `ServerMsg::ImageGone { terminal, screen, image, generation }` tells the client to forget one. The daemon remembers per client what it queued in full. A placement whose image is not queued yet is left out of that frame until it is (an image the emulator no longer has in that generation is left out too, and the next frame lists it again). An image the client was sent that is no longer in its screen's storage (deleted, replaced by a new generation, evicted by the 64 MiB limit) gets `ImageGone`, queued behind the frame that stops listing it, and a re-transmitted id sends the new generation's pieces and the frame listing it before the old generation's `ImageGone`; the storage is checked only while that screen is active, so entering and leaving the alternate screen neither forgets nor re-sends the other screen's images. A closed terminal's images are forgotten without `ImageGone`, a detached client's whole set is dropped. A client that did not attach with `images` gets none of these, and the daemon copies no pixels for it. Pixels are copied on the emulator thread (`TermHandle::with_emu`); when a new image appears in a frame the daemon pushes the frame without its placement, copies the pixels with the state lock released, then queues the pieces and a full frame of that terminal. The frames the drain hook below owes are built the same way. Full frames built on attach, resync, scroll, resize and panel change copy under the state lock. The byte budget is checked from the size the emulator reports, before any copy, and a terminal with a held-back image copies nothing more until its owed frame; an image whose pixels cannot be copied is remembered by generation and not asked for again. Clients share one copy of the pixels: the queue holds (image, offset, length) and cuts the 4 MiB piece when the writer takes it. The TUI client ignores both messages until it draws images.
- **Image queue class**: image pieces are a third class in the client queue, never dropped and bounded by bytes instead of by count: an image is queued only when the client's pending piece bytes plus the image's size stay within 64 MiB, or when no pieces are pending (so one image up to the storage limit always gets through). An image that does not fit is not queued, its placements are left out of that frame, and when the pending pieces have drained the queue tells the writer (`Next::Owed`, as `Next::Resync` does after dropped frames) and the daemon sends the client a full frame of each terminal it owes, which runs the same rules again. Pending pieces stay queued and are sent while the client is marked for a resync; `ImageGone` is a plain never-dropped message; a queued frame never goes out before the pieces queued ahead of it.
- **Several clients on one session** are allowed. PTY sizes follow the client that most recently sent input or a viewport, and the daemon's layout decides sizes and directional focus. Every client draws with the `layout_viewport` from the `SessionView`, cropped or padded to its own panel area.
- **Backpressure**: each client has a bounded queue. When it is full, the daemon drops that client's pending frames and sends a `full` frame once it drains. `Bye`, `Response`, `ImageGone` and the pieces of images (bounded by bytes, see Image queue class) are never dropped; for `SessionView` only the latest pending one per client is kept (a newer one replaces an unsent one), and views triggered only by title changes are sent at most 10 times a second.
- **Attention** (DECK-06): `ClientMsg::Focus(bool)` reports whether the client's outer terminal has focus (a client that never reported counts as focused). `PanelView.unseen` marks a panel whose hook-sourced agent went from `working` to `waiting` or `idle` while it was not the active panel of a focused client; the daemon then sends one `ServerMsg::AgentAlert { kind, status, project, panel }` to the session's most recently active client, which writes OSC 9 or a bell to the outer terminal as `notify` says. Names are stripped of control characters by the client.
- **Clipboard**: a program's OSC 52 copy (`ClipboardStore`) is forwarded to the session's most recently active client, which writes OSC 52 to the outer terminal; OSC 52 reads (`ClipboardLoad`) are denied.
- **Control requests** (DECK-05, `PROTOCOL_VERSION` 22 since `Request::Stats` and `Response::Stats(Stats)`, which carry the daemon's memory, descriptors, threads, CPU time, counts and per-terminal figures (DECK-23); 21 since `CellPx`, `Attach.cell` and `images`, `Viewport.cell`, `ReloadViewport.cell`, the image placement types, `Frame.images`, `ServerMsg::Image` and `ServerMsg::ImageGone` (DECK-19); 20 since `Theme` lost `icons`, `icon_images`, `glyphs`, `icon_glyphs` and `icon_colors` (DECK-20); 19 since `Action::MoveProject { project, to }` and `Action::MovePanel { panel, to }` (the daemon moves the item to index `to` of the session's spaces or of its space's panels, clamped to the last index, and answers `NoSuchProject` / `NoSuchPanel` for an unknown id; the active space and panel, the collapsed state and focus do not change, and the saved order is the new one); 18 since `Theme::icon_colors`; 17 since the panel area keeps every row (the floating bar takes no row); 16 since `CursorShape::Default`; 15 since `Request::ListAgentSessions`, `Response::AgentSessions`, `PanelLaunch::Resume` and `ActionError::InvalidSessionId` (DECK-11); 14 since `Action::NewPanelWith` (the daemon resolves `PanelLaunch::Agent(kind)` from `[agents.<kind>] command`, and `ActionError` gains `ProgramNotFound` and `LaunchFailed`); 13 added `icons` and `icon_glyphs` to `Theme` (12 added `Action::AutoNamePanel` and `Request::AutoNamePanel`; after 11, the agent status work, which added `AgentEvent`, `ClientMsg::Focus`, `ServerMsg::AgentAlert` and the resume keys of `Config` (`resume_agents`, `[agents.<kind>] resume` and `resume_latest`))) are thin wrappers over the same daemon functions as the attach client's actions: `Tree { session }` (answered by `Response::Tree`, the `SessionView`s with each terminal's `pid` and `keep` and each session's `attached_clients`), `NewProject`, `NewPanel` (project by `Target::Id` or `Target::Name`) and `NewTerminal` (answered by `Response::Created { id }`), `Focus`, `Close` (by id) `RenamePanel` and `AutoNamePanel` (answered by `Ok`). Terminal I/O: `Send { terminal, bytes, paste }` and `SendKeys { terminal, keys }` (answered by `Ok`; keys are encoded by the daemon with the emulator's current `Modes`), `Capture { terminal, lines, history, ansi }` (answered by `Response::Captured`, capped at 10,000 lines or 8 MiB) and `Wait { terminal, until, timeout_ms }` with `WaitFor::{Exit, Text, Idle}` (answered by `Response::Waited` when the condition holds; the connection stays usable meanwhile and a pending wait is dropped with its connection; responses carry no id, so a `Wait` answer can arrive after the answers of later requests on the same connection, and a client uses one connection per wait). The daemon keeps a removed terminal's exit status for 60 s (at most 256) for `Wait`, counted from the terminal's removal. A launch is a `LaunchSpec` (program, arguments, `--env` additions, directory); an empty directory means the default. Targets in the `DECK_*` variables are resolved by the CLI, which asks for the tree first; the daemon resolves only ids and project names. IDs are unique across kinds (one counter), so a bare id names a session, project, panel or terminal.
- **Agent session listing** (DECK-11): `Request::ListAgentSessions { kind, limit }` (an attached session only; a control client gets `Response::Error("no session")`) is the one request whose answer is not in order. `conn::dispatch` does not await it: `Shared::spawn_listing` starts a task in the connection's task set (dropped, and its OpenCode children killed, with the connection) that pushes `Response::AgentSessions { kind, sessions, error }` when done, and every failure is the `error` text, never `Response::Error`. A client routes the answer by `kind` and never gives it to a request queue that expects answers in order (the TUI picker's FIFO ignores it). See [agents](features/agents.md#listing-and-restoring-sessions).
- **Config and notices** (DECK-08): `Welcome { session, config }` carries the daemon's resolved config (the client never reads the file), and `ServerMsg::Config` sends the new one after every reload. `ServerMsg::Notice { level, text }` (`Info`, `Warning`, `Error`) carries daemon-side messages (a config error, a state file that could not be read) to every attached client, or, when none is attached, to the next client that attaches (the last 20 are kept, oldest dropped, a repeat of the same level and text replaces the earlier one; all are also in `daemon.log`). The client shows them in the floating bar: `muted` for 2 s (info), `warning` for 4 s, `error` for 6 s, one after the other.
- **Bytes, not strings**: paths and environment entries travel as raw bytes (`deck-core::wire`), so non-UTF-8 names round-trip; `encode` returns an error (never panics) and refuses a payload over the 16 MiB limit.
- Every message type is defined once in `deck-core`, with a round-trip test.

## Client

- **Terminal setup**: raw mode, alternate screen, mouse capture, bracketed paste and focus events through crossterm (the `ratatui::crossterm` re-export, so the versions always match). The outer terminal is restored on every exit path, including panics (cursor shape included). A blocking thread reads crossterm events and forwards them to the tokio runtime over a channel; crossterm's `event-stream` feature is not used. The cursor shape is set with crossterm's `SetCursorStyle`; a terminal whose program never chose a shape (or reset it with `CSI 0 SP q`) gets `CursorShape::Default`, which restores the outer terminal's own shape (`DefaultUserShape`).
- **Screen**: sidebar (left, toggleable), the active panel's terminals, and a one-row floating bar. The sidebar and the panel area take every row of the window (`layout::panel_area` keeps the last one). Prompts and confirmations are centered dialogs over everything else (`draw::draw_dialog`). The floating bar (`bar.rs`: `App::bar`, `bar_covers`, `draw`) shows only while the prefix is armed, a resize repeat or a border or separator drag is on, scroll mode or sidebar focus is on, or a flash is live; it is centered over the last row of the panel area, never drawn under a dialog or in a too small window, and a press on its cells is never sent to a program. The sidebar header shows the session name and the `+ New space` chip with one clickable cell of padding on each side. A single terminal fills the panel area with no border and no title; borders with titles come with several terminals in DECK-03. The client keeps a mirror of each visible terminal's lines and redraws on change, at most every 16 ms.
- **Bottom bar and hover**: the sidebar area's last row is the bar and the row above it a spacer (none when the area is under 8 rows); `list_height` is the area minus the header and these two rows, and `ensure_visible`, the wheel and the drawing share it. `App.hover: Option<Hover>` (`NewProject` for the chip on the header row, `New` and `Restore` on the bar, `Row(Sel)` for a space, panel or terminal row of the list, keyed by ids so a scroll or a change of rows recomputes it; a chip press sets `chip_down`, a row press is the ordinary click) is client-local and never sent. A `Moved` event over the sidebar sets it from `hover_at` and marks the screen dirty only when it changed; a `Moved` or any other event over the panel area, a focus loss, an overlay opening, a click and a wheel event clear it. The client keeps the last pointer position and recomputes the hover from it after a sidebar wheel scroll, a resize and a `SessionView`. A left press on a chip sets `chip_down` to its `Hover`; the release on the same chip starts the `prefix P` flow (`NewProject`), opens the New menu for `App::new_target()` (`New`: the sidebar selection's project in sidebar focus, else the active project; `no space` flash without one) or opens the restore dialog (`Restore`). The New menu sits above the bar with its left edge on the first column (`menu_rect`). Every icon is two cells (`sidebar::ICON_CELLS`, `icon_slot`: the image placeholder, or the glyph and a blank); the New menu and the restore dialog's headings draw their icons the same way, and so do the sidebar's chips (`Icon::New`, `Icon::Resume`; `sidebar::draw_chip`: a space, the icon's slot and, from 26 columns, a space and the label, then a space).
- **Sidebar row gestures** (`sidebar.rs`): a left press on a space, panel or terminal row only records it (`App.row_press`); the release on the same row (compared by id) acts (a terminal row sends `FocusPanel` then `FocusTerminal`), a pointer that reaches another row from a terminal row drops the press (a terminal row never drags), and the pointer reaching another row of the list turns the press into a drag (`App.row_drag`), which owns the mouse like the separator drag until the release. The target is computed on the daemon's rows, which stay drawn while dragging (the dragged row dimmed, the target row with a `➤` caret and its content shifted two columns), and the release sends `Action::MoveProject` or `Action::MovePanel` when the target differs from the item's place; the moved order (`sidebar::rows_with` with a `Reorder`) is drawn from the release (`App.row_drop`) until the answer to that action. The client never reorders its mirror.
- **New menu**: `App.menu: Option<NewMenu>` (`menu.rs`) is an overlay (`overlay_open` counts it) opened by the bottom bar's `+ New` chip, `prefix N` (`new_menu`) and `n` in sidebar focus. It takes keys after the dialogs and the picker, before the prefix, and `on_mouse` routes to it before the sidebar and the drags; its position is computed on every use (right above the bottom bar with its left edge on the sidebar's first column, clamped to the window; top right without a sidebar). An item sends `Action::NewPanel` or `Action::NewPanelWith`, and an error answer flashes as for any action. A `SessionView` without its project closes it with a flash.
- **Context menu**: `App.context: Option<ContextMenu>` (`context.rs`) is an overlay (`overlay_open` counts it) opened by a right press (`Down(Right)`) on a sidebar row (`open_row_menu`, from `hover_at`; a terminal row opens the terminal menu of that terminal, `New terminal` sending `FocusPanel` then `NewTerminal { panel: Some(..) }`) or on a cell of a terminal of the active panel (`open_terminal_menu`; on an unfocused terminal after the `FocusTerminal`, only when `deck_has_right`: no mouse reporting, Alt held or scroll mode). The target is a terminal, panel or project id, so items act on it whatever the focus; `confirm_close_terminal` takes the terminal. It has the mouse right after the restore dialog and before the New menu, and the keys before the New menu; the rect is computed from the pressed cell on every use. `New panel` opens the New menu with `NewMenu.anchor` set to that cell. The menu remembers the sidebar row it was opened from (`ContextMenu::row`, `None` from the grid) and the sidebar draws that row with the hover background; `draw.rs` draws the menu after the New menu and before the dialogs. A `SessionView` without the target closes it (`check_context_target`).
- **Restore dialog**: `App.restore: Option<Restore>` (`restore.rs`) is an overlay (`overlay_open` counts it), opened by the `Resume` chip, `prefix R` (`restore`) and `R` in sidebar focus. It takes keys after the dialogs, the picker and the New menu, before the prefix, and `on_mouse` routes to it before the menu. Opening sends three `ListAgentSessions` requests directly (never through `App.requests`); `Response::AgentSessions` is routed by `kind` from `App::response`, and dropped when the dialog is closed. Each column is `Load::{Loading, Error, Ready}` with its own selection and scroll offset; the geometry (90% by 80%, one column under 60 window columns) is computed from the window on every use. Resuming picks the project with `deck_core::agent_sessions::project_for` and sends `Action::NewPanelWith { project, launch: PanelLaunch::Resume { kind, session_id, cwd } }`, with the same `launch_result` bookkeeping as the New menu.
- **Sidebar width**: `App.sidebar_width` is client state, the single source of the width the client draws and reports. It starts from the config, is replaced by a config reload that changes `sidebar_width`, is set by dragging the separator (a left press on column `sidebar_width` starts a drag that is never forwarded to a program; motion applies `layout::clamp_sidebar_width(cols, pointer)` at most every 33 ms and on release, and sends `Viewport` per change), is clamped to the window at start, on a config change and on an outer resize, and is never written to `config.toml`. The client also watches `SIGWINCH` itself (tokio) and feeds a changed size to `on_event` as a resize, because crossterm 0.29's poll returns the TTY or the signal event and drops the other's edge-triggered readiness, which lost a resize that arrived with typed input. A release lost to a `Moved` event, a focus loss, a key, an overlay or a resize ends the drag.
- **Input**: keys arrive as crossterm events. The prefix key (default `Option+Space`, `M-Space`) starts a binding; macOS reserves `Ctrl+Space` for input-source switching, so deck would never receive it, and terminals where Option is not Alt send a non-breaking space for `Option+Space`, which counts as the prefix too (only for `M-Space`); any other key is encoded to bytes by `deck-core::keys::encode(key, modes)` (xterm encoding, honouring application cursor keys) and sent to the focused terminal. Pasted text is wrapped in bracketed-paste markers when the terminal asked for them. Mouse events go to the terminal when it enabled mouse reporting, otherwise the client handles them (focus, scroll, sidebar, border drags, text selection); an Alt press selects text even then (see Text selection). The kitty keyboard protocol is not used in v1, so keys such as `Shift+Enter` cannot be told apart from `Enter`. Character bindings ignore `Shift` (`X` matches a shifted `x`), and crossterm's `Ctrl+4`…`Ctrl+7` encode to `0x1C`…`0x1F`. The client also restores the outer terminal on `SIGTERM` and `SIGHUP`, and refuses to attach when stdin or stdout is not a TTY.
- **Text selection** (DECK-15, `select.rs`): `App.text_sel: Option<TextSel>` is client-local and built from the mirror's lines, so the selection covers only the rows on screen. A left press in the focused terminal starts one when the program has no mouse reporting, when Alt is held, or in scroll mode; the drag and release are then the client's wherever the pointer goes (clamped to the terminal's screen). The release copies with the same OSC 52 output as `ServerMsg::Clipboard` and flashes `Copied N characters` in the floating bar (nothing is copied or flashed for an empty selection). A frame of that terminal that is resized, scrolled or changes a selected row's text clears it (a full frame, sent on every change while scrolled back, clears it only then), as does any other press; a drag cut short by that is swallowed until its release.
- **Look**: colours by role only (accent, muted, warning, error, ok), mapped to the outer terminal's ANSI palette by default so the user's theme applies; overridable in `[theme]` (DECK-08). Unicode box drawing with rounded corners by default (`border_style`); Nerd Font glyphs are never required. When `COLORTERM` is not `truecolor` or `24bit`, the client draws every RGB colour (theme and terminal contents) as the nearest 256-palette colour.
- **Icons** (DECK-20): every icon deck draws is a `deck_core::icons::Icon` with a fixed Unicode and a fixed Nerd Font glyph (`icons::unicode`, `icons::nerd`; one cell each). The client draws each in a two-cell slot (`sidebar::icon_slot`) in the form of its `Tier` (`deck-tui/src/tier.rs`), decided once per client run in `deck-tui/src/caps.rs` from what the terminal answers (DECK-20 sub-spec 02). The terminal is named by its XTVERSION reply (`Ghostty`, `Kitty(version)`, `WezTerm`, `ITerm2`, `Other`), else by the environment (`TERM_PROGRAM`, `TERM`, `KITTY_WINDOW_ID`, `GHOSTTY_RESOURCES_DIR`, `WEZTERM_EXECUTABLE`; Terminal.app never answers XTVERSION and is found by `TERM_PROGRAM=Apple_Terminal`). `Image` when the graphics query answered `OK` (or, when neither new query was answered, the environment says Ghostty or kitty as in the icon images paragraph below), the terminal draws Unicode placeholders (Ghostty, kitty 0.28 or later) and has truecolor, outside tmux, Zellij and deck. Else `Nerd` when the terminal bundles the Nerd Font symbols (Ghostty, WezTerm, kitty 0.36 or later; not inside a deck panel), or a font check finds Nerd Font glyphs: iTerm2's profile font (`defaults export com.googlecode.iterm2 -`, the profile of `ITERM_PROFILE` or `Default Bookmark Guid`; its `Non Ascii Font` alone when `Use Non-ASCII Font` is on, else its `Normal Font`), Terminal.app's profile font (`defaults export com.apple.Terminal -`, the font data of `Default Window Settings`), or an installed font with U+F120 and U+EAB4 (`fc-list ':charset=f120 eab4' family`, else, on macOS, when `fc-list` is missing, fails or times out, a Nerd Font file in the macOS font folders; iTerm2 and Terminal.app do not use it). Else `Unicode`. `caps.rs` is the one module of `deck-tui` that spawns programs (`defaults`, `fc-list`; directly, no shell, stdin and stderr closed, killed after 1 s) and lists font folders; the check runs on a thread started after the probe and sends its answer on a channel of the client loop, which upgrades `Unicode` to `Nerd` once and redraws (the tier never downgrades). Behind tmux, Zellij, screen or in a deck panel nothing sees through the multiplexer: its own answers decide, and only the installed-font check applies in a deck panel. In the `Image` tier every icon but the drag caret is an image (below). Claude's icon is always `#d97757` (`convert::claude_color`). Nothing in `[theme]` changes an icon.
- **Icon images** (DECK-12, DECK-20): in Ghostty and kitty every icon but the drag caret is an image in place of its text icon: program icons, space carets, status marks (sidebar rows and grid titles) and the unseen marker (`deck-tui/src/graphics.rs`). Whether icons are images follows the `Image` tier decided in `caps.rs` (above); the environment rules in this sentence are only the fallback when the terminal answered neither XTVERSION nor the graphics query: `TERM` is `xterm-kitty` or `xterm-ghostty`, `TERM_PROGRAM` is `ghostty`, or `KITTY_WINDOW_ID` is set; never with `TMUX`, `ZELLIJ` or `DECK` set (deck sets `DECK` in every panel), `TERM` starting with `screen` or `tmux`, or without truecolor. Each icon is a 64x64 alpha mask in `crates/deck-tui/assets/icons/` (`graphics::mask`, `include_bytes!`; the SVG sources, Hugeicons 4.4.0 under the MIT licence, the OpenCode source, the trademark note and the commands that made the masks are in its `README.md`). Before every draw the client registers the (icon, RGB) pairs the frame needs and sends each new pair once: `App::send_images` draws the frame once into a scratch buffer, and every image slot (`sidebar::icon_slot`, used by sidebar rows, grid titles, the New menu and the restore headings) notes the pair it wants, in the colour it draws in, so the pre-pass cannot differ from the drawing. A pair not sent yet is drawn as its glyph. Each new pair is sent once, tinted, through the kitty graphics protocol as a virtual placement two cells wide and one tall (`a=T,U=1,f=32,c=2,r=1`, base64 in chunks of at most 4096 bytes, `q=2` on every command so no reply reaches the input). The icon is then two cells (`U+10EEEE U+0305 U+0305`, `U+10EEEE U+0305 U+030D`) with the 24-bit image id (from `0xDEC001`) as their foreground colour, ordinary symbols for ratatui, in the same two-cell icon column as the text icons; the cells have no modifiers and show the row's visible colours (`REVERSED` resolved, `Images::cell_for`). The loader (DECK-20 sub-spec 04) is the `spinner` mask turned clockwise by 6 degrees per frame (`graphics::spinner_frame`, 60 frames, bilinear, computed once): the first time a colour needs it the pre-pass registers and sends all 60 frames of that colour, so a tick never waits on a transmission. The frame shown is `floor(elapsed * 60) mod 60` of the time since the client started (`App::started`, `App::spin_frame` set by `tick`), the same for every spinner; in the `Image` tier the spinner timer fires on the next 1/60 s boundary, in the text tiers every 100 ms. A tick redraws through ratatui, which writes only the changed cells (the spinners' two). The id colour is built in `convert.rs`, the one exception to the rule that colours come from the theme. The tint is the icon's colour resolved to RGB (Claude's orange for Claude, the status marks' and carets' theme roles, else the row's; `sidebar::icon_style`, which on a reversed row puts it in the background): the outer terminal's foreground (OSC 10) for `default`, its own palette for indexed colours 0 to 15 (OSC 4 queries `4;0` to `4;15` in the start-up query, before the DA1 request), the xterm cube and grey ramp above. On exit or detach the client deletes every image it sent (`a=d,d=I`) before it leaves the alternate screen; a crash leaves them in the terminal until its window closes. The end-to-end harness removes `TERM_PROGRAM`, `KITTY_WINDOW_ID`, `GHOSTTY_RESOURCES_DIR`, `WEZTERM_EXECUTABLE`, `TMUX`, `ZELLIJ` and `DECK` from the client's environment, so the tests run in the `Unicode` tier, so the developer's own terminal never changes a test.
- **Program images** (DECK-19, `deck-tui/src/placed.rs`, `diacritics.rs`): a client that attaches with `images: true` (the `Image` tier, which implies truecolor, and a known cell size) gets each image's pixels in `ServerMsg::Image` pieces and the placements of every `Frame` (kept in `TermMirror.images`). `Program` assembles the pieces per (terminal, screen, image): offset 0 restarts, a gap or an older generation discards, the pixels stay until `ImageGone`, the terminal leaving the session view or a new session. One id allocator (`Images::alloc`, 24 bits, never 0, ids given back after their delete are reused) serves icon images and programs. Before a draw `App::draw_frame` (`send_program_images`) builds, for each placed placement of the active panel's terminals that has none, an outer image: `placed::canvas` is a pure function that cuts the `source` rectangle, scales it to the rendered `pixels` (bilinear, alpha-weighted, only the part that lands on the canvas) and puts it at the top left of a transparent canvas of `cols x cell width` by `rows x cell height` pixels (`cols`, `rows` cut to the 297 of the diacritics table; no canvas over 64 MiB of RGBA); it goes out as `a=t,f=32` in chunks of at most 4096 base64 bytes plus one virtual placement (`a=p,U=1,c,r`), all with `q=2`. The key of an outer image is (terminal, screen, image, generation, source, pixels, drawn cols and rows, cell size), so moving or scrolling a placement sends nothing. After the draw `finish_images` deletes (`a=d,d=I`) the outer images no placement used and gives their ids back. The cells (`draw::draw_images`, after a terminal's text and selection, before borders and overlays) hold U+10EEEE with the row and column diacritics and the outer id as the foreground, on the background underneath; a wide character cut by the rectangle leaves a blank cell. Virtual placements are ignored (sub-spec 07), and a program's own placeholder cells are drawn as blanks, images on or off, so a program's image id never reaches the outer terminal. On exit or detach the client deletes every outer image before leaving the alternate screen. The image capability is decided once per connection, when `Hello` is built (`App::program_images`): if the cell size later becomes unknown the client keeps receiving pixels it does not draw, and if it was unknown at attach images stay off until the next connection. The e2e harness's `Builder::kitty()` and `cell_px` make a test's outer terminal a Ghostty with a pixel size.

## Agents

- Every terminal gets `DECK=1`, `DECK_SOCKET`, `DECK_SESSION_ID`, `DECK_PANEL_ID` and `DECK_TERMINAL_ID` in its environment, so a program inside deck (an agent, or the agent's hooks) can find and control its own place through the control API.
- **Status** (`none`, `working`, `waiting`, `idle`, plus `active` and `quiet` for process-only detection) is detected every second from the PTY's foreground process (`platform::foreground_process`; `[agents.<kind>] process`), and sharpened by hook events (`Request::AgentEvent`, `source: Hooks`, which win). Hooks come from the agents' own hooks (Claude Code hooks, Codex hooks, an OpenCode plugin), which call `deck agent-event`. Without hooks, deck recognises an agent by the PTY's foreground process name and shows only activity. Details: the agent status spec (DECK-06).
- Agents are relaunched after a daemon restart with their resume command (DECK-06 sub-spec 05). `TerminalState.agent` (`AgentResume { kind, session_id }`, `#[serde(default)]`, no `state.json` version bump) is saved for a terminal with an agent state; a change of kind or session id marks the state dirty. Once `shutting_down` is set the daemon ignores `AgentEvent` and detection changes. A restored shell terminal runs `/bin/sh -c '<resume command>; exec "$0" "$@"' <shell> <shell_args...>`, an explicit agent program is replaced by the resume command; the templates are validated in `deck-core::agents` (`check_template`, `valid_session_id`, `resume_command`) so no shell syntax or unvalidated id reaches the command line. See [agents](features/agents.md#resume).
- **Session listing** (DECK-11, `server/listing.rs`): the daemon reads each agent's recent sessions with the session's environment and the pure parsers of `deck-core::agent_sessions`. Claude (`projects/*/<uuid>.jsonl`, newest `limit × 2` by mtime, 256 KiB head each) and Codex (date directories newest first until `limit × 2` rollouts, read line by line to the first prompt, 4 MiB per file) walk the disk on `spawn_blocking`; OpenCode runs `opencode session list` through `tokio::process` (the `process` feature of the approved `tokio`) in every project root and `~`, with the session's environment, two at a time inside 8 s, 4 MiB of output each. Nothing runs under the state lock or in `dispatch`, and titles and directories are never logged (`Shared::notify_client` sends the missing-directory notice to the acting client alone, unlogged and not kept for later clients). `Options.listing` (`ListingStats`: files opened, bytes read, most children at once) is the test hook. `PanelLaunch::Resume` renders the agent's `resume` template through `NewPanel` like a launch (`server/launch.rs`).

## Persistence

- The daemon writes `state.json` (serde_json, `{ "version": 1, "next_id", "last_attached", "sessions" }`, the types in `deck-core::state`) after every change to a saved field, debounced: the first change schedules a save 500 ms later and changes inside the window join it. A save runs off the async workers: it writes `state.json.tmp` (mode `0600`), fsyncs it, renames it over `state.json` and fsyncs the directory. Safe against process crashes; best effort against power loss. A failed save is logged and retried on the next change.
- **Shutdown** (`kill-server`, `SIGTERM`, `SIGINT`, `SIGHUP`, the last session ending) first sets the `shutting_down` flag: terminals ending because of it are not removed and no timed save runs. Then it saves synchronously and hangs up the terminals. The file holds the model (ids, names, name sources, order, ratios, focus, collapsed state), the ID counter, the order of `last_attached`, and for each terminal its program, arguments, launch-spec environment additions (never the client's environment, never `DECK_*`) and its directory. Not scrollback, titles or exit statuses.
- **Start**: take the lock, delete a leftover `state.json.tmp`, read `state.json`, validate it (`StateFile::validate`: ids and names made unique, dangling focus and `last_attached` dropped, invalid ratios replaced, `next_id` moved past every saved id), rebuild the model, bind the socket, then launch the terminals in a background task, so clients can connect while they start. Every terminal starts in the first directory that exists of its saved cwd, its project root and the home directory (the daemon checks with `metadata().is_dir()` itself: portable-pty would silently use the home directory), with the daemon's own start environment plus the saved additions. A terminal that cannot start is removed like an exited one and reported in a `Notice`; one that fails at once is removed and reported too, and never ends its session. A file it cannot parse is moved aside to `state.json.bad-<unix seconds>` and the daemon starts empty with a notice; a file with a newer `version` stops the daemon (`DaemonError::NewerState`) without touching it.
- **Working directories.** A terminal's `cwd` (model and `SessionView`, saved in place of its launch directory) comes from OSC 7 when the shell reports it: the reader thread feeds each PTY chunk to `deck-core::osc7::Osc7Scanner` (streaming, 4 KiB limit per sequence, hosts empty, `localhost` or the machine's name in full or short form; paths must be absolute UTF-8 without NUL) and the bytes still reach the emulator unchanged. A terminal that reported once is never polled again. For the others a daemon task ticks every 5 s (`DECK_TEST_CWD_POLL_MS` for tests) and asks `platform::process_cwd(pid)` for all of them in one `spawn_blocking` call, with the pid of the terminal's own child, never the PTY's foreground process group. A changed cwd goes to the clients in a `SessionView` and marks the state dirty only when the saved directory (live cwd, else launch directory) changes. `NewTerminal` starts in the first existing directory of the panel's focused terminal's cwd, its launch directory and the project root. A control launch with an explicit `cwd` uses it as given and fails when it is not a directory. A `SessionView` shows the launch directory until a live one is known.
- Details: the persistence spec (DECK-04).

## Paths

| What                 | Path                                                                                                                                                           |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Config               | `$XDG_CONFIG_HOME/deck/config.toml`, default `~/.config/deck/config.toml` (both OSes)                                                                          |
| State and log        | `$XDG_STATE_HOME/deck/`, default `~/.local/state/deck/`: `state.json`, `state.lock`, `daemon.log` (rotated at start when over 10 MiB, one `daemon.log.1` kept) |
| Socket and lock      | `$XDG_RUNTIME_DIR/deck/` if set, else `$TMPDIR/deck-<uid>/`, else `/tmp/deck-<uid>/`: `deck.sock`, `deck.lock` (holds the daemon's pid)                        |
| Everything, isolated | `DECK_HOME=<dir>` puts the config at `<dir>/config.toml`, state in `<dir>/state/` and the socket in `<dir>/run/`. Used by tests and `just run`.                |

Socket paths must stay under 100 bytes (the macOS limit is 104); `deck` refuses a longer one with a clear error. That is why `just run` puts its `DECK_HOME` in `${TMPDIR:-/tmp}/deck-dev-<8 hex characters of just's sha256() of the checkout path>` rather than under `target/`: a socket inside `.worktrees/<slug>/target/` would exceed the limit. `just run` also clears the `DECK` and `DECK_*` variables of an enclosing deck session: `DECK_SOCKET` wins over `DECK_HOME`, so without that the dev build would reach the installed daemon, and its attach would refuse to nest.

## Config

`config.toml` at the path in [Paths](#paths) (`~/.config/deck/config.toml` by default on macOS and Linux), every key optional; a missing file means the defaults. Parsed in `deck-core::config`; an unknown key is a warning, a bad value an error naming the key. The daemon is the only reader (DECK-08): it reads the file at start (an invalid one means the defaults and an error notice), sends the config to clients in `Welcome`, and every second (`DECK_TEST_CONFIG_POLL_MS` for tests) compares the file's modification time, change time, size and inode with the last read, so an edit, a save through a rename and a deletion (back to the defaults) are all seen. A change is validated with `config::validate`; an invalid file that changed again by the next poll (an editor still writing) is read again, else it keeps the last good config and sends an error notice with its line and column. A valid one is sent to every client as `ServerMsg::Config` with a `config reloaded` notice (and one warning notice when there are warnings); clients apply only what changed, and `shell`, `shell_args` and `scrollback_lines` only affect terminals started afterwards. `[theme]` holds colour roles and the border style (DECK-08); the keys that used to change the icons (`icons`, `icon_images`, `[theme.glyphs]`, `[theme.icon_glyphs]`, `[theme.icon_colors]`) are gone and warn (DECK-20); the client draws every non-terminal element from a `deck-core::theme::Theme`. `crates/deck-core/src/config/default.toml` documents every key with its default and is printed by `deck config default`; a `deck-core` test requires it to parse to `Config::default()` and to mention every key of `Config` and `Theme` and every action, either set or as a commented `# key = …` example (for optional keys such as `shell`), so a spec that adds a key or an action fails that test until it documents it there. `config::validate(text)` returns every error and warning with a line and column (used by `deck config check`; it never starts a daemon). `Config` is the resolved wire form (plain types, postcard-encodable); the string-or-array and string-or-integer TOML shapes are read and converted while loading. Keys are added by the spec that needs them, starting with `prefix`, `shell`, `shell_args`, `scrollback_lines` and `[keys]` (DECK-01). A `[keys]` entry maps an action to one key or a list of keys.

## Testing

- **Unit tests** next to the code, run by cargo-nextest. `deck-core` carries most of them: layout tables, key encoding, protocol round trips, config parsing.
- **Daemon tests** in `crates/deck-daemon/tests/` start a daemon in-process on a temp `DECK_HOME` and talk to it through the protocol.
- **Stress suite** (DECK-23) in `crates/deck/tests/stress.rs`: ignored tests (flood, many terminals, churn, attach loop, control loop, soak) that load a real daemon hard and for long and assert bounds on what `deck stats --json` reports (memory, descriptors, threads, CPU, and how soon a key typed during a flood echoes). `just stress [filter]` runs them in a release build, one at a time; `DECK_SOAK_SECS` sets the soak's length (default 600). Each writes `target/stress/<scenario>.json`, the soak also `soak.csv`. `just check` does not run them. The hidden `DECK_TEST_LEAK_FD=1` makes the daemon leak a descriptor per terminal it starts, for the test that churn's descriptor check fails. Bounds and measured values: [docs/features/stats.md](features/stats.md#the-stress-suite).
- **End-to-end tests** in `crates/deck/tests/` use the harness in `crates/deck/tests/support/`: it runs the real `deck` binary in a PTY of a fixed size with a temp `DECK_HOME` (config: `shell = "/bin/sh"`, `shell_args = []`, `PS1='$ '`), feeds its output to an alacritty_terminal emulator and records the raw bytes, and offers `send_keys`, `wait_for_text(text, timeout)`, `screen_text()`, `cell(row, col)`, `raw_output()` (for asserting on escape sequences), `tty_mode()` and `capture(name)`, which writes the screen to `target/e2e-captures/<test>/<name>.txt`. DECK-01 sub-spec 04 defines it (`support/mod.rs`; `support/sys.rs` and `crates/deck-daemon/tests/support/sys.rs` are the only test modules allowed `unsafe`, for `tcgetattr` and `kill`). The harness sets `DECK_TEST_NO_FONT_CHECK=1` for the client, which skips the font checks (iTerm2's and Terminal.app's profile fonts and the installed-font check), so a developer's fonts never change a result; it is a test seam, not a setting. Every test kills its daemon at the end, and harness daemons get a hidden `DECK_TEST_PARENT_PID` and exit when that process is gone, so a test killed by nextest leaks nothing. Timing: upper bounds are asserted only in daemon tests with an injected clock; end-to-end tests assert lower bounds and generous upper bounds (3 to 5 times the expected time). Tests run on macOS and Linux.

## Platform modules

`unsafe` and `libc` calls live only in `crates/deck-daemon/src/platform/` (`macos.rs`, `linux.rs`: a process's cwd (DECK-04), the PTY's foreground process and its argv (DECK-06), exit signals, and the daemon's own figures for `Request::Stats` (DECK-23): `self_stats()` returns `SelfStats` with resident memory, open descriptors, threads and user and system CPU time, each `Option`, from `proc_pidinfo` (`PROC_PIDTASKINFO`, `PROC_PIDLISTFDS`) and `getrusage` on macOS and from `/proc/self/{statm,fd,status}` and `getrusage` on Linux), `crates/deck/src/platform.rs` (`setsid` when starting the daemon, `geteuid`, `dup2` of the daemon's stderr onto its log, `kill` for `kill-server`'s `SIGTERM` fallback, `poll` and `read` on stdin for the client's colour query, which `deck-tui` cannot do in safe code and takes as a closure), and the test support modules `crates/deck/tests/support/sys.rs` (`tcgetattr`, `kill`) and `crates/deck-daemon/tests/support/sys.rs` (`kill`). The lints do not enforce placement (`#![allow(unsafe_code)]` opts a module out); review does. The peer uid uses tokio's safe `peer_cred()`. Each `unsafe` block has a `// SAFETY:` comment.

## Releases

- **Local**: `just install` runs `cargo install --path crates/deck --locked` into `$PREFIX/bin`, `~/.local/bin` by default.
- **CI** (GitHub Actions, repository `marcosmoura/deck`): `.github/workflows/ci.yml` runs `just check` on macOS and Linux for pushes to `main` and pull requests, with the tools from `.mise.toml` (`jdx/mise-action`). `.github/workflows/stress.yml` runs `just stress` on macOS and Linux once a day and on manual dispatch, with `DECK_SOAK_SECS=1800`, and uploads `target/stress/` as an artifact even when a scenario fails. `.github/workflows/release.yml` runs on a pushed `v<version>` tag, which must match the workspace version, and on pull requests that change a `Cargo.toml`, `Cargo.lock`, `.mise.toml` or the workflow itself (the build matrix only: the tag check, packaging and publishing run for tags). It installs Rust and Zig, builds `deck` in release mode on native runners for `aarch64-apple-darwin`, `x86_64-apple-darwin`, `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu` (Ubuntu 22.04, for glibc 2.35), packs each as `deck-<version>-<target>.tar.gz` (the binary and `README.md`) with a `.sha256` file, and uploads them to the GitHub release with `gh` (`gh release upload --clobber` when the release exists, `gh release create` otherwise; a `concurrency` group keyed on the tag allows one run per release). `ci.yml` also runs `just lint-ci` (actionlint and shellcheck) on the Linux runner.
- **Release pull requests** (`.github/workflows/release-please.yml`, `release-please-config.json`, `.release-please-manifest.json`): every push to `main` runs `googleapis/release-please-action` (pinned by SHA, `simple` release type (`rust` fails on the virtual workspace root), `initial-version: 0.1.0`, `package-name: deck`, tags `v<version>`, `bump-minor-pre-major`, changelog sections `feat`, `fix`, `perf`, title `chore(repo): release <version>`) with the fine-grained token `RELEASE_PLEASE_TOKEN` (Contents, Pull requests and Issues, read and write, on this repository only; the default `GITHUB_TOKEN` would trigger no workflows). It keeps a release pull request up to date; the root `Cargo.toml`'s `[workspace.package] version` is updated through an `extra-files` entry (`type: toml`, `jsonpath: $.workspace.package.version`). A **fix-up job** runs on each push to release-please's branch (`release-please--branches--main`): `cargo update --workspace` and `oxfmt CHANGELOG.md`, and commits `Cargo.lock` and `CHANGELOG.md` back through the GitHub contents API with the same token, so CI runs again; a push with nothing to fix commits nothing. Fine-grained tokens expire and must be renewed. Known gap: the release is published before the build finishes, so for about 10 minutes the latest release has no assets and `install.sh` fails with a clear message.
- **Homebrew tap**: after the publish job, the `homebrew` job of `release.yml` downloads the release's `.sha256` files, renders `packaging/homebrew/deck.rb.in` with `packaging/homebrew/render.sh <version> <dir>` (it fails naming a target whose sum is missing; `packaging/homebrew/check.sh`, run by `just lint-ci`, renders it with fake sums and fails on a left placeholder) and writes `Formula/deck.rb` in `marcosmoura/homebrew-tap` through the GitHub contents API with the fine-grained token `HOMEBREW_TAP_TOKEN` (Contents read and write on the tap only; it expires and must be renewed), message `deck <version>`. A failure there does not undo the release; rerun the job. The formula installs the prebuilt binary (`brew install marcosmoura/tap/deck`; the full name trusts the formula, which Homebrew 7 requires of third-party taps). The tap holds only deck (recreated on 24 Nov 2026, DECK-29) and checks the formula on every write: its `tests.yml` runs `brew style`, `brew audit --strict`, `brew install` and `brew test` on macOS and Linux, and Dependabot keeps its actions current. It has no branch protection, so the release job commits to `main` directly.
- **Cutting a release**: merge the open release pull request (the user does, never an agent). release-please then tags `v<version>` and creates the release, the tag fires `release.yml`, which builds the four targets, uploads the tarballs and checksums and updates the tap. Never bump the version or push a tag by hand. The repository must be public: the ARM Linux runners are free only there, and a private repository's aarch64 Linux job never starts.
- **`install.sh`** (POSIX `sh`, at the root) picks the target from `uname`, downloads the latest release (or `DECK_VERSION`), checks the SHA-256 and installs `deck` into `${DECK_INSTALL_DIR:-$HOME/.local/bin}` through a rename. `DECK_REPO` and `DECK_DOWNLOAD_URL` override where it downloads from (the latter is how it is tested against a local tarball).

The workspace denies Clippy's `unwrap_used`, `expect_used`, `panic` and `indexing_slicing` lints. The root `clippy.toml` allows these in tests. Integration-test helpers and closures that Clippy misses use scoped exceptions. Production exceptions document the invariant or test hook at the point of use. `just lint` checks every workspace target with warnings denied.
