# Agents

Read when you need how deck shows what a coding agent (Claude Code, Codex, OpenCode) is doing.

## States

A terminal that runs an agent has an agent state: its kind, a status and a source.

| Status    | Glyph | Meaning                                                                               |
| --------- | ----- | ------------------------------------------------------------------------------------- |
| `waiting` | `!`   | The agent needs you (warning colour, bold).                                           |
| `working` | `⠋`…  | The agent works: a spinner (one frame every 125 ms in every form).                    |
| `active`  | `⠋`…  | Found by its process, and it printed in the last 2 s (accent colour, like `working`). |
| `idle`    | `●`   | The agent is done and waits for a prompt.                                             |
| `quiet`   | `○`   | Found by its process, and it printed nothing for 2 s.                                 |
| none      |       | No agent: nothing is drawn.                                                           |

Urgency, most to least: `waiting`, `working`, `active`, `idle`, `quiet`, none. The sidebar shows, in the status slot at the right end of a panel row, the icon of the panel's most urgent terminal, in a two-cell slot (the glyph, then a blank cell). The icons are fixed (see [config](config.md#icons)); the spinner has 10 frames in Unicode and 6 in Nerd Font glyphs, one frame every 125 ms in either, and the colours come from the theme: the spinner `accent`, `waiting` `warning` and bold, `idle` `ok`, `quiet` `muted`. Under a row with an agent the sidebar shows its [activity line](sidebar.md#the-activity-line): the activity, else the status in words.

A panel with an agent is named after it in the sidebar: the agent's title without its spinner, else the first line of its first prompt (see [sidebar](sidebar.md#the-sidebar)). A grid border title for an agent terminal reads `<status slot> <kind> · <name>` in place of the number (`╭─ ⠹  claude · Fix login bug ──╮`, the slot two cells wide). There is no status icon without an agent. In Ghostty and kitty the spinner is Hugeicons' `Loader`, eight spokes that fade behind the brightest one, turning once a second, one spoke at a time (the same frame on every spinner); in other terminals it keeps its glyph frames. The client redraws the spinner only while one spins and only while one is on screen: a spinner scrolled out of the sidebar's view, or hidden by another panel, stops its timer until a draw shows it again.

## Detection by process

Every second the daemon asks the operating system for the foreground process of each terminal's PTY (`sysctl` on macOS, `/proc` on Linux) and compares its program name with `[agents.<kind>] process` (a list of names; defaults: `claude`, `codex`, `opencode`). A login dash and a script interpreter (`node claude.js`) are looked through, and an extension is ignored. The same tick sets each terminal's `program` to that name (`ls --json` shows it) and leaves it as it was when the process cannot be read. A match gives the state `source: process`: `active` while the terminal printed in the last 2 s, else `quiet`. When the agent leaves the foreground the state is cleared.

```toml
[agents.claude]
process = ["claude", "my-claude-wrapper"]
```

An unknown kind or field under `[agents]` is a warning.

## Hook events

`Request::AgentEvent` sets the state with `source: hooks`, which wins over the process: `status`, `session_id` and the first line of a `prompt` (at most 200 characters, the first one of a session). A new `session_id` replaces the stored one and resets the first prompt. Rules:

- A hook state is cleared 3 s after the agent left the foreground.
- A hook `working` with no event and no output for 60 s falls back to the process state.
- Typing into a terminal whose hook status is `waiting` sets it to `working` (the user answered). Focus reports do not count.

The event also carries an **activity**: one line, at most 80 characters, on what the agent does now (`running cargo test`, `editing sidebar.rs`, `worker: reading sidebar.rs`, `needs permission: run the tests`, or the first line of its last message when it stopped). `deck agent-event` builds it from the payload (`deck-core::agents::describe_hook`, below), so only the line reaches the daemon, never the tool's input or the whole message. OpenCode's path differs: `deck agent-event` reduces the event (`reduce_opencode_event`) and sends it with `Activity::Keep` and `at_ms` 0 (a caller with no clock), and the daemon's `OpenCodeTracker` builds the line from it. The request says what to do with the line (`Activity::Keep`, `Clear` or `Set(text)`) and when `deck agent-event` started (`at_ms`, Unix milliseconds). The daemon cleans and cuts a `Set` again (first non-blank line, control characters removed, 80 characters), because a hook is not trusted to have done it. Rules:

- Claude Code runs its hooks asynchronously, so events can arrive out of order: the daemon keeps, per terminal, the `at_ms` of the last activity it applied and ignores the activity of an older event (its status still applies). An `at_ms` of 0 (a caller with no clock) is never older.
- A state that is cleared (the agent left the foreground, `SessionEnd`, a hook state that fell back to the process state after 60 s) loses its line, and so does a `waiting` state the user answered by typing.
- The line is part of the terminal's agent state in `SessionView`; a change of the line alone is pushed through the same throttle as titles (at most one view per 100 ms, and a last one after a burst), a change of status at once. It is never saved in `state.json`, never written to `daemon.log` and never put in a notification ([privacy](privacy.md)).
- Without a line, a client shows the status in words (`deck-core::agents::describe_status`): `working`, `needs you` (`waiting`), `ready` (`idle`), `printing` (`active`), `quiet`.

`deck ls --json` shows `"agent": null` or `{ "kind", "status", "source", "session_id", "activity" }` per terminal (`activity` is a string or `null`). The hooks that send these events are installed with `deck hooks install` (next section).

## Hooks

`deck hooks install claude codex opencode` makes the agents report what they do, so deck knows when they work, wait for you or finish. It edits only the agents' own config files, only when you run it.

| Command                           | What it does                                                                 |
| --------------------------------- | ---------------------------------------------------------------------------- |
| `deck hooks install <agent>... `  | Adds deck's hooks; `--print` shows what would be written and writes nothing. |
| `deck hooks uninstall <agent>...` | Removes only deck's hooks.                                                   |
| `deck hooks status`               | One line per agent: `installed`, `not installed` or `stale`.                 |

`--print` prints the whole file as it would be written, not only deck's part: for Claude Code that is your `settings.json` with everything in it, an `env` block with API keys included. Do not paste its output somewhere public.

- **Claude Code**: `$CLAUDE_CONFIG_DIR/settings.json` (default `~/.claude/settings.json`), under `hooks`: one entry per event (`SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PermissionRequest`, `Notification`, `Stop`, `SessionEnd`), no matcher, `"async": true`, so the agent never waits for deck.
- **Codex**: `$CODEX_HOME/hooks.json` (default `~/.codex/hooks.json`) with the `{ "description", "hooks" }` wrapper: `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PermissionRequest`, `Stop`, `Interrupt`, `SessionEnd`, each with `"matcher": ""` and `"timeout": 2`. A Codex hook is synchronous, so `PreToolUse` adds one `deck agent-event` run (a few milliseconds, 500 ms at most) before each Codex tool call. An install from before `PreToolUse` existed is `stale` in `deck hooks status` until `deck hooks install` runs again. Codex only runs hooks you reviewed: open `/hooks` in Codex and trust them. Codex keys a trust entry by a hash deck cannot compute, so `status` cannot tell whether you did and says `installed (trust them in /hooks if Codex asks)`. `status` also tells when deck entries are found in `config.toml`; Codex loads both files and warns about duplicates. Codex runs its hooks in a background server that every Codex on the machine shares (`codex app-server`, unless Codex is started with `--no-daemon`), with the environment of the terminal that started it, so a hook's `DECK_TERMINAL_ID` can name another terminal or one that is gone. `deck agent-event --agent codex` therefore asks the daemon for the tree first and sends the event to the Codex terminal that already has the payload's `session_id`; else to a Codex terminal in the payload's `cwd`, else in any directory, preferring one with no session yet, then the focused terminal of an attached session (where you just started Codex or typed a prompt), then the one the environment names; with no Codex terminal it keeps the environment's. Two Codex terminals in one directory with no session yet are told apart only by focus.
- **OpenCode** (v2): a TUI plugin, `plugins/deck/tui.js`, in `$OPENCODE_CONFIG_DIR/plugins/` when that variable is set, else `$XDG_CONFIG_HOME/opencode/plugins/` (default `~/.config/opencode/plugins/`). It is a TUI plugin, not a server plugin, on purpose: by default OpenCode v2's TUI connects to one shared background server that is started detached with the environment of whichever terminal started it first, so a server plugin would report every session with that terminal's `DECK_TERMINAL_ID`. Each TUI loads the subdirectories of its `plugins/` directory and runs a TUI plugin (`tui.js`, a default export `{ id: "deck", setup(ctx) }`) in its own process, where `DECK_TERMINAL_ID` is the right one; the server finds no server entry in the directory and loads nothing. `setup` calls `ctx.data.listen`, which gets the events of every session on the shared server, so the plugin keeps only the events of its own sessions: the session of the route it shows and its root (`ctx.ui.router.current()`, `ctx.data.session.root`), and the subagent sessions a `session.created` with a `parentID` of one of them starts. It forwards `session.created`, `session.status`, `session.idle`, `permission.asked`, `permission.replied`, `session.inbox.enqueued` and `session.tool.called` by running `deck agent-event --agent opencode --event <type>` with the event (`{ "type", "data", … }`) as JSON on stdin, through `node:child_process` `spawn`, without waiting for it; the calls are chained on one promise queue so the events arrive in order; the cleanup it returns unsubscribes. For the activity line it also watches three more v2 events and keeps its processes few: `session.tool.input.started` (`{ sessionID, id, name }`) only records the tool's name for its call id, because `session.tool.called` (`{ sessionID, id, input, executed }`) carries none; a `session.tool.called` of a root session is forwarded once per call id (at most 256 ids are remembered) with the name added and the input cut to its `command`, `description`, path, `agent`, the start of `patchText` and the first question's `header`; a `session.text.ended` (`{ sessionID, assistantMessageID, ordinal, text }`, one per finished text, never the streamed `session.text.delta`) is kept in memory for a root session as its first line only, and sent once, as an event of the plugin's own shape (`{ "type": "deck.text", "data": { "sessionID", "text" } }`), just before the turn's idle `session.status` or `session.idle` (a `busy` drops it). A turn so costs one process per event of today plus one per tool call plus at most one for its text, however long the answer streams. The plugin otherwise interprets nothing: the daemon keeps one `OpenCodeTracker` (`deck-core::agents`) per terminal, which drops events of subagent sessions (a session whose `session.created` has a `parentID`; at most 256 are remembered) except their `permission.asked` and `permission.replied`, which still set `waiting` and `working` without replacing the root's session id, maps a turn to `working` and `idle`: OpenCode v2.4 sends `session.execution.started` and `session.execution.succeeded` (`interrupted` and `failed` end it too, with `interrupted` or `failed` as the line), earlier v2 `session.status` `busy`/`idle` (and the deprecated `session.idle`); it maps `permission.asked` to `waiting` and `permission.replied` to `working`, a question (`form.created`, its session in `form.sessionID`) to `waiting` with `asking: <the form's title, else its first field's>` (else `asking a question`) and `form.replied` or `form.cancelled` to `working`, and takes the first prompt from `session.inbox.enqueued` when its `item.type` is `user` (`item.payload.text`). `retry` statuses and other events are ignored. The same tracker builds the activity line with the words of the tool line below: a `session.tool.called` (v1: a `message.part.updated` with a `tool` part whose `state.status` is `running`, once per call) is the tool's line, with OpenCode's `shell` (v1 `bash`), `read`, `edit`, `write`, `patch`, `grep`, `glob`, `webfetch`, `subagent` (v1 `task`), `question` and `todowrite` mapped to the Claude Code rows (`shell` by its `description` when there is one, else `running <first line of the command>`; `patch` `editing <first file the patch names>`, else `editing files`; `subagent` `dispatching <agent>: <description>`; `question` `asking: <header of the first question>`; `grep`, `glob` and `webfetch` show `searching` and `fetching a page`, since the pattern and the URL never reach the daemon; other tools `using <tool>`); `permission.asked` is `needs permission: <tool line>` (the line of the call named by `source.id`, v1 `tool.callID`, else of its `action`, v1 `permission`) and `permission.replied` restores the line of a call that was granted (`once`, `always`) and clears it for a rejection or an unknown call; `session.status` `busy` is `thinking` unless a tool already ran in the turn; `idle` is the first line of the turn's `deck.text` (Markdown marks removed, as for Claude Code's last message), else `done`. Events of subagent sessions give no line. The tracker remembers at most 64 call lines (80 characters each) and a text line, never an input. ## Attention

Hook-sourced states only (a process-only `active` to `quiet` pause happens all the time and never counts). When a terminal goes from `working` to `waiting` or `idle` and nobody is looking at it, its panel is **unseen**, and the daemon sends one `ServerMsg::AgentAlert { kind, status, project, panel, panel_id }`. A [running command](sidebar.md#running-commands) that ends while nobody is looking marks its panel unseen too, without an alert.

- **Looking** means the panel is the session's active panel and a client of the session has its outer terminal focused. A client reports focus with `ClientMsg::Focus(bool)` from the outer terminal's focus events, and again on every attach once it saw one; a client that never reported counts as focused, so a terminal without focus reporting never notifies for the active panel.
- **Unseen** panels are bold in the sidebar with the unseen marker (`•`, accent, a two-cell slot) after the name, until the panel is the active panel of a focused client. A collapsed space shows `!<n>` (warning) after its name when `n` of its panels wait.
- **The alert** goes to the one client of the session that sent input or a viewport last, and the client shows it as `notify` says: `"system"` (default) as deck's own desktop notification (below), `"terminal"` (old name `"osc9"`) as `ESC ] 9 ; <body> BEL` to the outer terminal, `"bell"` a lone `BEL`, `"none"` nothing. The body is `<kind> needs you · <space> › <panel>` for `waiting` and `<kind> finished · <space> › <panel>` for `idle`; control characters are stripped from the names. A panel nobody renamed is named after its terminal's title, or after the first line of the agent's first prompt, cut to 32 cells, so those words are in the notification (and in the notification history of the desktop, on a lock screen or a shared screen), in `deck ls`, in the shell completion menus and in `state.json` until the name changes. `notify = "bell"` or `"none"` keeps them out of notifications, and a panel renamed by hand keeps the name you gave it ([privacy](privacy.md#things-that-may-surprise-you)). OSC 9 shows a desktop notification in iTerm2, Ghostty and WezTerm and is ignored by terminals that do not know it (kitty uses OSC 99 and is not targeted). Inside tmux or over ssh it reaches the desktop only if they pass it through.
- **Jump**: `prefix a` (`next_attention`) focuses the next waiting terminal in sidebar order after the current one, wrapping; with none waiting, the next idle terminal in an unseen panel; with none, it flashes `no agent needs you`. Panels of collapsed spaces are included.
- **deck's own notification** (`notify = "system"`): on macOS the client runs `terminal-notifier` with title `deck`, the body as its message, `-group deck-<session>-<panel>` (a newer alert of a panel replaces its older one), `-execute` with `DECK_SOCKET='<the client's socket>' '<deck>' 'focus' '--session' '<session>' '<panel>'` (every word single-quoted for `sh`; a click runs it in launchd's environment, so it names the daemon's socket) and, when macOS gave the client its terminal app's bundle id (`__CFBundleIdentifier`, `com.mitchellh.ghostty` in Ghostty), `-activate` with it: a click focuses the panel and brings the terminal forward. On Linux it runs `notify-send --app-name=deck --action=default=Open --wait deck <body>` (`&`, `<` and `>` escaped, since notification daemons read markup; libnotify 0.7.9 or later, with a notification daemon that supports actions) and, when it prints `default` (the notification was clicked), runs the same `deck focus` with the client's `DECK_SOCKET`; Linux has no portable way to raise the terminal's window. The client decides once, when it starts, whether it can show its own notifications: a notifier on its `PATH` (absolute entries only), not over ssh (`SSH_CONNECTION` or `SSH_TTY` set: the notification would show on the remote machine, while OSC 9 reaches yours), and on Linux a desktop session bus (`DBUS_SESSION_BUS_ADDRESS`). When it cannot, `"system"` behaves exactly as `"terminal"`, the jump on focus return below included. A notifier that starts but then fails (an older libnotify that rejects `--action`) shows nothing and is not detected. With deck's own notification a click works at any time, and coming back to the terminal by hand never jumps. `__CFBundleIdentifier` is inherited from whatever started the client, so inside tmux it may name the app that started the tmux server, and the click brings that app forward.
- **Notification click without deck's own notification**: OSC 9 sends no click back, so the client uses the focus report. When it writes an alert (`notify` `"terminal"` or `"bell"`) while its outer terminal is unfocused, it remembers the alert's panel (a newer alert replaces it). If its outer terminal gains focus within 10 s, and the panel is still there and needs you (a waiting terminal, or an idle one in an unseen panel), the client focuses that space, panel and terminal, and forgets the alert; otherwise it only forgets it (also when a prompt, menu or overlay is open). The program in the terminal it lands on gets the focus-in report, if it asked for them. Only the client that wrote the alert jumps, `notify = "none"` never jumps, and a client that never reported focus never jumps. The limit: deck cannot tell a click on the notification from any other way back, so switching to the terminal by hand within 10 s jumps too. In a terminal with several windows or tabs, the click brings forward a window of the terminal's own choosing. Ghostty, iTerm2 and WezTerm do not report clicks on OSC 99 notifications (checked in their sources), so nothing more precise exists yet.

Limitations: a session with no attached client alerts nobody (its panels are still marked unseen for the next attach), and the session picker shows no agent status.

```toml
notify = "bell"
```

## Starting an agent in a new panel

The action `NewPanelWith` (sent by the [`New` menu](sidebar.md#the-new-button-and-menu) and by DECK-11's restore) starts a new panel in a space that runs an agent's `[agents.<kind>] command` (defaults `claude`, `opencode`, `codex`), in the space's directory. The command is run directly, with no shell, as the program of an explicit-program terminal (like `deck new-terminal -- <program>`), so the panel closes when the agent quits. The panel is added, active and focused like `prefix c`, and is named at once after its program (`claude`).

```toml
[agents.claude]
command = "claude --model fast"
```

`command` is a program and arguments split on whitespace, with the same limits as a resume template (no quote, backslash, `$` or other shell syntax) and no `{session_id}`. An empty command, one that breaks those limits, or a program with a `/` that is not an absolute path is a config error naming the key (`agents.claude.command`).

Before anything is created the daemon looks the program up: a program with a `/` must be an executable file, any other is searched in the `PATH` of the session's environment, which is the one of the client that created the session (it is not refreshed when another client attaches, and the daemon's own `PATH` is never used). When it is missing, no panel is created, focus stays and the client flashes `"opencode" not found in PATH (set [agents.opencode] command)`. If the program is found but cannot be started (the space's directory is gone, say), the error is the operating system's text and nothing is created either. A script with a bad interpreter line starts, fails and closes its panel like any program that exits at once.

`deck new-panel -- <program>` passes its own program and does not use `command`.

The terminal is saved and restored as an explicit-program terminal. When the program's name is in the kind's `process` list (the default `command` always is), the agent is detected and [resumed](#resume) after a daemon restart. For a `command` whose program is not in `process`, the agent is not detected, and a restart relaunches the command fresh.

## Listing and restoring sessions

The daemon lists each agent's recent sessions for the restore dialog (`Request::ListAgentSessions { kind, limit }`, the 50 newest by default, `limit` clamped to 1 to 100) and can start a panel that resumes one (`NewPanelWith` with `PanelLaunch::Resume { kind, session_id, cwd }`). Both use the environment of the client that created the session (`HOME`, `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `XDG_DATA_HOME`, `PATH`), never the daemon's, and a listing needs an attached session (a control client gets `no session`).

| Agent       | Where sessions are read from                                                                                    | Bounds                                                                                                                    |
| ----------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Claude Code | `$CLAUDE_CONFIG_DIR/projects/*/<uuid>.jsonl`, default `~/.claude/projects` (one level; `agent-*.jsonl` skipped) | The newest `limit × 2` files by modification time, 256 KiB read from the head of each                                     |
| Codex       | `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-*.jsonl`, default `~/.codex/sessions`                                  | Day directories newest first until `limit × 2` rollouts; read line by line up to the first prompt, at most 4 MiB per file |
| OpenCode    | `opencode session list --max-count <limit> --format json`, run once, in `~` and never in a space root           | 8 s, 4 MiB of output; at most 2 at a time over all requests                                                               |

- Each request is answered from its own task, so a slow agent delays neither the others nor the connection's input and actions. The answer, `Response::AgentSessions { kind, sessions, error }`, arrives when it is ready, out of order with other answers; clients route it by `kind`. A failure (a command that is missing, prints no JSON array or times out) is the `error` text (`could not run opencode session list`, `timed out`) with an empty list, never a `Response::Error`; a missing agent directory is an empty list without an error.
- Codex candidates are chosen by file name (creation date) and sorted by modification time, so an old session resumed recently can be missed when more than `limit × 2` newer rollouts exist. The program of the OpenCode listing is the first word of `[agents.opencode] command`.
- **OpenCode is listed from `~` only.** OpenCode loads the configuration of its working directory and of every directory above it, with no trust prompt: it runs the plugins it finds there (`.opencode/plugin/`) and starts the MCP servers they configure. Listing in a space root would therefore run a repository's code as you, just because the restore dialog was opened (security finding Q-4 of the [privacy review](../reviews/2026-11-24-privacy.md)). OpenCode v2 lists the sessions of its working directory's project only, so OpenCode sessions started in a repository are missing from the dialog until DECK-40 lists every project without entering one. The child gets `~` as its `PWD` as well and no `OLDPWD`: the session's own name the directory it was created in, and a program can take `PWD` for its working directory. A session whose `HOME` is missing or not an absolute path lists no OpenCode session. Any `opencode` call can also start OpenCode's background service, which then keeps running with the session's environment.
- `PanelLaunch::Resume` runs the agent's `resume` template with the session id (invalid ids are refused with `not a valid session id`; the program is looked up in the session's `PATH`, and a missing one names `resume`: `set [agents.claude] resume`). The terminal starts in the session's directory, or in the space root with the warning `<dir> no longer exists; started in <space root>` when it is gone. The panel is saved and resumed after a daemon restart like any agent panel.
- Titles and directories go only to the client that asked: the daemon log has counts and timings only, and `state.json` has none of them.

## The restore dialog

The `Resume` button at the right of the sidebar's bottom bar, `Option+Space R` (binding `restore`, in the Session group of the help) and `R` in sidebar focus open a centered overlay, 90% of the window wide (at least 60 columns) and 80% high (at least 10 rows), with a filter line, three columns (`Claude Code`, `OpenCode`, `Codex`, each with its count) and a hint line. With no space, they flash `no space to restore into` instead.

- **Opening** sends three `ListAgentSessions { kind, limit: 50 }` requests at once. Each column shows a muted `loading…` until its own answer comes, then its sessions, its error in the warning colour, or a muted `no sessions`. One slow agent never holds the others up, and closing the dialog drops answers that arrive later. An answer that arrives late from a dialog just closed can briefly fill a reopened one, until the fresh answer replaces it.
- **Rows**: two lines per session, the title and, in muted text, `<directory> · <age> ago` (the directory cut from the left, `~` for the home directory). The selection starts on the first row of the first column that has any; each column scrolls on its own to keep it in sight. Each column heading starts with its agent's icon, two cells and a space (`✻  Claude Code (50)`), an image where images are on. Below 60 window columns one column shows at a time, `‹ ✻  Claude Code (12) ›`, and `Tab` switches.
- **Filter**: typing filters all three columns at once; every word must be in the title or the directory (case-insensitive). The selection moves to the nearest row. `Esc` clears the filter, a second `Esc` closes. [Keys](keys.md#restore-dialog).
- **Mouse**: hovering a row highlights it, a click selects it and a click on the selected row resumes it, the wheel scrolls the column under the pointer, a click on a header moves the selection to that column, a click outside closes the dialog.
- **Resuming** opens a new panel in the space whose root holds the session's directory (the longest root; the active space on a tie), else in the active space, running the agent's `resume` command in the session's directory (see above for a directory that is gone). The dialog closes at once and the new panel is active and focused. A refusal (`"claude" not found in PATH ...`, `not a valid session id`) is a 4 s error flash and creates nothing.

## Resume

After `deck kill-server` or a reboot, each terminal that had an agent in the foreground when the state was saved comes back with that agent reopened on its conversation (`resume_agents = true`, the default). The saved state keeps, per terminal, the agent's kind and its `session_id` (from hooks; `null` when only the process was seen). The state is saved 500 ms after the agent or its session id changes, and once more, before the terminals are hung up, when the daemon stops. While the daemon is shutting down it ignores agent events and detection changes, so an agent's `SessionEnd` hook or the hang-up's exits cannot clear what resume needs.

- **A shell terminal** is relaunched as `/bin/sh -c '<resume command>; exec "$0" "$@"' <shell> <shell_args...>`: `sh` runs the agent, then replaces itself with your shell and its `shell_args`. Quitting the agent leaves you in your shell, in the same directory. Nothing is typed into a shell or written to its history, and the terminal's launch spec stays the plain shell, so a later restore without an agent starts a plain shell.
- **A terminal that was started with the agent as its program** (`deck new-terminal -- claude`) is relaunched with the resume command as its program and arguments, in its original directory with its original `--env`. No shell is involved. The program is the one of the configured template (found on the daemon's `PATH`), so the terminal's original arguments (`--model x`, say) are dropped. A terminal whose program is not an agent is relaunched as saved.
- The `resume` template is used when a valid session id is known, else `resume_latest`.

```toml
resume_agents = true # false: restore a plain shell

[agents.claude]
resume = "claude --resume {session_id}"
resume_latest = "claude --continue"
```

| Agent    | `resume`                          | `resume_latest`       |
| -------- | --------------------------------- | --------------------- |
| Claude   | `claude --resume {session_id}`    | `claude --continue`   |
| Codex    | `codex resume {session_id}`       | `codex resume --last` |
| OpenCode | `opencode --session {session_id}` | `opencode --continue` |

A template is a program and arguments, split on whitespace. `{session_id}` may appear only as a whole argument of `resume`, never in the program, and `resume_latest` has none. A quote, a backslash, `$`, a backtick or any other shell syntax (`; & | < > ( ) * ? [ ] { } # ~ !`) is a config error that names the key (`deck config check` shows it), because the command is joined with spaces and run by `sh -c`. A session id is used only when it matches `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$` (it can never start with `-`); any other id is dropped, logged, and `resume_latest` runs. The program of a template is found on the daemon's `PATH`. The resumed agent is detected again like any other: the `sh` wrapper of a resumed shell terminal is recognised as the agent it runs, and the restored terminal has its agent state from the start, so a second restart resumes it again.

Limitations:

- **Several agents of one kind in one directory** each resume their own session when their session ids are known (hooks installed). Without ids every one of them runs `resume_latest`, which opens the same most recent conversation each time.
- **Staleness.** After a crash or `kill -9` the restore uses the last save: an agent that quit in the last 500 ms may be relaunched, and a `session_id` that changed in that window may point at the previous conversation. A hook-reported agent also stays in the state for up to 3 s after it leaves the foreground (see the hook rules above), so quitting the agent and stopping the server within 3 s relaunches it.
